## Decide the Core Now

**Non-tool LLMAgent forms implement SDK Agent.** It accepts the SDK's literal text/conversation requests and returns genuine SDK generation and streaming results, with `version`, `id`, and `tools` compatibility properties. Use a shared language execution core backed directly by `generateText` and `streamText`. The SDK owns model requests, tool loops, termination, output parsing, events, usage, and provider cancellation. Casai owns configuration, application-context validation, prompt preparation, hooks, and additive history metadata.

**Every callable component has an ordinary call and `.run()`.** Each has a main property: `prompt` on LLMAgent, `template` on Template, `script` on Script, `execute` on Function, and the SDK input field on a specialized component. Input modifiers set its type, never its name. Ordinary calls take inputs, not execution settings. On a plain LLMAgent a first-position string or message array is the new prompt, followed by optional context and history; with a configured prompt, context can be supplied first. Rendered forms take source, context, and history as applicable. `.run()` takes named inputs and per-call settings, with native SDK controls on LLM operations and cooperative signal forwarding on Function. Script/Template timeouts and shared deadlines wait for Phase 7; native engine abort support is separate. All callable components expose `.config`. Streaming mode is inherited from a parent component and cannot be switched off by deriving a child; `.asStream` enables it on LLMAgent and Template. Independently called components keep their own mode. LLMAgent's SDK `.generate()` and `.stream()` explicitly select their operation regardless of the ordinary-call mode.

**The shorthand caller is the primary API in every phase.** This principle applies to all current and future callable components. Keep its input forms, including positional source/context/history forms and Cascada named calls. `.run()` supplies named inputs and optional execution overrides. Whatever the ordinary caller cannot supply, but the operation requires, must be satisfied by resolved configuration, including inheritance. Reusable `Config` fragments may be incomplete; final callable components must meet these fixed requirements. See [ordinary calls and required configuration](#ordinary-calls-and-required-configuration).

**Resolve configuration and call inputs before schema processing.** Config fragments may be incomplete, and final components may leave call-suppliable inputs unresolved. Preserve established merge/override laws and require what remains missing through call types. Keys declared by `inputSchema` are application/tool input; undeclared configured keys are private execution dependencies outside that schema. Resolve final application input from configured values and call arguments, then parse once and use the returned value. The input schema determines public application values; its acceptance does not authorize a model to replace private bindings. The shared execution path enforces the confirmed private-binding policy; production changes must retain its runtime/type and transport verification. Configured execution bindings are never automatically published as SDK arguments. Custom callbacks must not mutate inputs; preserve native parser copying and the accepted native `.readonly()` behavior. Every schema boundary, including outputs and stream elements, uses its parsed value. See [Phase 2](#schema-parsing-and-context-isolation).

**Template, Script, and Function use native Casai contracts.** Their calls return what the template or program produces: a string, or a text stream with `.asStream`, for Template; the program's value for Script and Function, which is a stream when their schema declares one. Reuse context, input validation, compatible configuration inheritance, and tool adaptation. Do not manufacture SDK steps, usage, assistant messages, or UI events, or maintain parallel native and SDK output schemas. Template remains text-only. Script and Function produce native structured values.

Workflow interchange happens at an application's input/value boundary: extract `.value` from an LLMAgent result in an explicit adapter, written as application code rather than provided by Casai, then give a coded implementation the same input and returned value type. Streaming interchange needs an adapter with declared stream capabilities; a plain complete-value function does not gain them implicitly. See [the public composition examples](../README2.md#interchanging-components-in-workflows).

Keep SDK result fields unchanged. Add `value` for final application output and `messageHistory` for conversation state. Execution mode changes delivery, never output selection: collecting a successful `value` stream must yield the same data as that execution's final parsed `output`. Unrestricted loops buffer candidate output until finality is known. Keep SDK `stream` for live execution events and `steps` for completed step records, with no new activity aliases. See [the output and result contract](#output-and-result-contract).

Keep `generateText` and `streamText` as the execution backend rather than wrapping `ToolLoopAgent`. They already own the tool loop and expose settings such as `onChunk`, `onError`, and `onAbort` that the installed `ToolLoopAgent` public settings type omits. Using that class would require workarounds for the agreed surface. It can run a single step, but step count is independent of backend choice and Agent assignability. The [Agent contract](https://ai-sdk.dev/docs/reference/ai-sdk-core/agent) requires neither that class nor a particular stopping condition.

A custom model/provider is not needed for native composition. If a concrete application later needs coded logic behind the SDK chat protocol, assess an explicit opt-in adapter separately. A provider backed by the public `LanguageModelV4` contract would let the SDK construct real results; do not commit to a Casai adapter or hand-built SDK result emulation now. See [custom provider guidance](https://ai-sdk.dev/providers/community-providers/custom-providers).

### Loader Composition and Inheritance

**Agreed design (2026-10-28), not implemented.** See the self-contained [loader guide](../README2.md#loader-composition-and-inheritance) for examples. This replaces the earlier named-group and ordinary-replacement proposals; it is separate from the completed Phase 3 simplification trial.

Cascada owns recursive composition. An array is an ordered chain; `raceLoaders(array)` races its entries. Keep the existing name and exactly one array argument, accepting configuration-driven lists of any length. An array inside the competitor list is one chain competitor: `raceLoaders([[a, b], c])` races the A-then-B chain against C. Preserve group boundaries instead of flattening them. The main race use is adding independent resource collections: discover which loader holds each requested name concurrently. Duplicate copies may race too, with completion order selecting the result; ordered overrides use a chain.

Casai re-exports native `raceLoaders` and adds only these inheritance directives:

- `loader: raceParent(group)` races the child group against the inherited group.
- `loader: overrideParent(group)` uses the supplied group without automatically adding the parent.
- Both directives occupy the whole property. Disallow nested/multiple parent directives; their contents can freely nest chains and races. Advanced composition can reference `parent.config.loader` explicitly inside `overrideParent(...)`.

Omitting `loader` inherits it. The ordinary parent/child lookup order when both supply a plain loader remains open. Do not silently settle it as part of implementation. Current child-first ordering and empty/undefined inheritance remain current behavior, not evidence that every new directive has the same clearing semantics.

The implementation should remove Casai's `RaceGroup`/named-group aggregation, executable-to-description recovery, anonymous-members registry and special group reconstruction. Resolve the parent directive during configuration inheritance, leaving Cascada a native composition. No Cascada parent operators or replacement policy are needed.

Ordered overrides must also affect relative imports: `[overrides, base]` can load `pages/main` from `base` and `./part` from `overrides`. Keep logical resource names and group resolution scope distinct from physical source paths. A race retains its selected member's scope, including an ordered chain, without searching unrelated competitors for relative imports. Preserve cache invalidation, pending-request sharing, miss caching, `noCache` and reload policy; do not remember one winning loader for unrelated resources.

Current native probes establish nested races and chains containing races, but nested chain arrays fail in both source and build. Add recursive runtime/types support and verify grouping, start order, relative overrides, cache/update behavior and empty/single-member lists. Environment fallback continues on `null` and stops on actual loader errors; races return the first success, miss if all miss, and report an error if none succeeds and one fails. Already-started work is not cancelled. The standalone native `loadString` utility currently falls back after errors too: resolve that existing contract difference explicitly if sharing its implementation.

Update exports, runtime/types, inheritance consumers and documentation together when implementing. README2 marks the agreed API as pending; README.md continues to describe the working API. The published Cascada documentation should distinguish existing composition from the recursive-chain and relative-override work.

## Phase Dependencies and Implementation Order

The eight phases separate improvements to existing components from the new Agent API. Their numbers give a preferred implementation order, not a strict dependency chain. Land focused changes with their own verification; use ordinary task lists within each phase rather than lettered subphases. Phase 3 needs the shared preparation and stream primitives from Phase 2, not every optional coded-component optimization. Phase 4 is independent continuation convenience: it does not gate the initial LLMAgent release, specialized components, or native streaming. Phase 7 depends on Cascada async call context, independently of Phase 6 streaming and future native abort support.

| Phase | Depends on | Implementation scope |
| :--- | :--- | :--- |
| 1: Result augmentation (implemented) | Current components, installed engine, and SDK | Shared final-output `value`, lazy history, genuine SDK results and native cancellation across all four LLM factories; remove legacy response overrides |
| 2: Existing component foundations | Phase 1, existing merge/source rules and installed schema/SDK interfaces; renderer completion uses the selected newer chain-resolution runtime | Merge-first parsing, private dependencies, SDK tool-default projection, parsed values, coded-component `.run()`/`.config`, execution metadata and keyword normalization, JavaScript stream schemas/collectors, Function producers, and Script iterable returns |
| 3: LLMAgent | Phase 1 result augmentation and the shared preparation/stream primitives from Phase 2 | Replace the four LLM factories; implement the new rendered positional calls and preparer tool registries, SDK Agent interface, `.asStream`, basic conversation history, unified application context/hooks, and completed streaming-tool output |
| 4: Tool continuations | Phase 3's conversation-history support | `resume()`, approval responses, and externally supplied tool results; optional for the initial LLMAgent release |
| 5: Specialized AI components | Applicable Phase 2/3 infrastructure and SDK APIs; not Phase 4; no new Cascada features | Operation adapters and result types derived from SDK contracts and the agreed tool-result mappings; recheck experimental APIs against the implementation version |
| 6: Cascada streaming integration | Phase 2 stream infrastructure, Phase 3 for LLMAgent composition, and new Cascada capabilities; not Phases 4/5 | Native `stream`/`tstream` channels, live Script returns, Template streaming, runtime kinds, source-order snapshots, and Cascada-owned validation and failure semantics |
| 7: Async call context and deadlines | Phase 2 invocation conventions, Phase 3 for LLMAgent integration, and Cascada async call context shared with telemetry; not Phase 6 or native abort | Inherit absolute end times and call ancestry implicitly, enforce SDK deadlines at dispatch, and bound Function/Script/Template waits with timeout races; add native interruption when available |
| 8: Out-of-order streaming | Phase 6 and Cascada's positioned streams (`at()` and positioned views) | Deferred positioned delivery |
| Future features | Applicable Cascada telemetry reporting and native abort capabilities, building on Phase 7 context | Workflow usage/telemetry APIs and actual engine interruption; see [abort.md](abort.md) and [future.md](future.md) |

### Design Status

The [Phase 2 review status](#phase-2-existing-component-foundations) records the immutable binding prototype for two confirmed requirements: configured public values satisfy required input fields, and arguments override tool context, which overrides configuration. The [public API/type proof](phase2-public-api-proof.md) joins bounded declaration capability, usable call signatures, and an explicit binding contract under its original policy. The later [private-data investigation](phase2-private-boundary-review.md) revised that policy and bare-tool support; the [combined proof](phase2-composed-api-proof.md) establishes bounded feasibility under the confirmed protection rules. Production projection, factory integration and current-engine consumer reviews are now implemented and verified; the newer compiler handoff remains separate acceptance work. The unified `_toolOptions` metadata API is settled. New LLM public conventions belong to Phase 3 LLMAgent; retiring factories receive shared correctness fixes only.

The target contracts retain named input objects, flat implementation context, fallback tool-function bindings, separate model arguments and application-supplied tool data, and final-output `value` with buffering when needed. Streams use ordinary consumption with lazy validation and no added replay guarantee. Cascada owns its complete-value and native `stream`/`tstream` error semantics: a complete return is healthy or poison/failure, and a stream ends at its first error after any valid prefix. Casai forwards those contracts rather than defining different consumer views. Stream schemas and tool collection apply only to a root stream; object field order has no calling semantics.

Remaining implementation work includes the newer-runtime acceptance for Phase 2, LLMAgent in Phase 3, continuations in Phase 4, specialized adapters in Phase 5, and the deferred Cascada integrations. The Phase 6 runtime bridge does not block Phase 2's JavaScript stream contracts. Rearranging the plan does not reopen the settled public call conventions. See [tool execution context](#tool-execution-context) and [the result contract](#output-and-result-contract).

Phase 1 is implemented in [result augmentation](../src/augment-result.ts), used by all four LLM factories across ordinary calls, `.run()`, and all prompt renderers. It adds top-level `value` to all results and `messageHistory` to text results while preserving SDK response and callback fields. Object results alias native `object`; history is deferred because the SDK object APIs return no generated messages. The old `messages.ts` implementation and augmented callback contracts are removed. Mock fixtures also prove SDK Agent/UI-helper compatibility. Phase 2 applies the confirmed schema/context corrections and final coded-component conventions to existing components. Phase 3 introduces LLMAgent; shared deadlines remain deferred to Phase 7.

### Error Types

**Error classification decision (2026-10-25):** centralize Casai error classes in `src/errors.ts`. `ConfigError` covers invalid configuration and unsupported schema/binding contracts, even when discovered lazily. The separate `ValidationError` covers invalid call arguments and Casai-owned input, context, output and stream-element validation, including unknown or undecided approvals in `resume()` and unknown tools in `executeTool()`. Keep `ScriptError` and `TemplateError` for their existing engine boundaries. Preserve SDK error types and causes for SDK-owned failures. Cascada owns poison propagation and native return behavior: complete objects are healthy or a poison/failure outcome, while `stream`/`tstream` terminates at the first error after any valid prefix. Casai adds no poison scanner, partial-object repair, consumer-dependent stream behavior, or separate export protocol. Ordinary JavaScript Function producers still need their declared schema validation, and LLMAgent `value` needs SDK failure adaptation. See [Phase 6 lifecycle](#lifecycle).

Casai-owned argument/schema failures on ordinary calls, `.run()`, and the injected tool runner reject with `ValidationError`, retaining the native validation error as cause. Actual SDK tool validation retains native SDK errors such as `InvalidToolInputError` and native context-validation errors. Do not expose an unhandled schema `ValidationResult` or add an error-translation layer around SDK execution. Cascada may wrap a coded runner's rejection through its normal render/script error path; retain that cause chain. Application execution failures keep their native behavior.

The injected runner owns input/context validation even when the registered definition is a plain native SDK tool. Wrap those two validation boundaries, leaving execution and preliminary-stream failures unchanged. For private/trusted-context failures, the public `ValidationError.message` names the stage/tool without concatenating native validation text or values; retain the original error only as `cause` for trusted diagnostics. Native `TypeValidationError.message` can serialize its rejected private context. If that error escapes an injected call inside an outer model tool, the SDK turns it into model-visible tool output. This is a concrete reason for the existing error boundary, not a general error-redaction layer. Preserve actual native SDK-owned context-validation behavior and developer-authored execution errors. Verify both generation and streaming through the next normalized provider request, rather than relying on JSON serialization of Error objects.

`ValidationError` does not extend `ConfigError`; runtime-validation consumers must update their catches. Use `instanceof` to distinguish these classes. Classification follows the failed contract, not merely creation versus invocation time: missing required model configuration, unsupported schema metadata/projection and a tool's absent stream-schema declaration remain `ConfigError`. Shared configuration validators select `ValidationError` for invalid invocation overrides without changing validation order, parsing or merging. Sharing a descriptor preserves parsing/execution semantics while the SDK and coded callers retain their own outer error classes.

Binding preparation owns its captured tool-context validation too. Wrap that parse at its source with a stage-only `ValidationError.message` and the native error as `cause`, before it can escape through metadata preparation, the SDK input validator or an injected call. Label it tool-context validation, not application-input validation. Preserve the SDK's outer argument/approval errors and original native context-schema identity. A fresh binding on approval continuation can be validated before tool metadata is prepared; native streaming can publish an invalid-approval `tool-error` before preparation rejects, even with zero provider requests and rejected history promises. Test that error text and UI chunks with a message-surfacing `onError`, alongside generation rejection, valid continuation, no executor entry, and metadata-first/validation-first/injected access. Causes remain trusted diagnostics and must not be serialized to users. This boundary does not promise to sanitize native-owned validation or arbitrary callback errors.

Test confidentiality across nested owners, not only at the immediate validator. Trusted code can pass a private value into an injected native tool's input, and a rejected component output can contain private data. Their Casai-owned validation failures retain native causes but expose only safe stage summaries, including after passing through another registered component. Assert the sentinel is absent from the actual next provider request, response messages and streaming UI errors; assert that the next request exists. Lazy element validation has the same ownership rule at iteration time. These checks do not authorize suppressing native producer/body errors or sanitizing intentionally returned application values.

Native streaming diagnostics are a separate disclosure sink from provider requests and UI streams. `streamText` and `streamObject` log full errors through `console.error` unless an execution `onError` handler is supplied; private causes are intentionally retained. Document explicit handlers for sensitive contexts, test Casai forwarding without redacting native errors, and capture the native default in characterization tests so fixture secrets do not reach test stderr. The installed ToolLoopAgent exposes no public `onError`; a UI error formatter alone does not change server logging.

### Confirmed Schema and Context Decisions

- **Security revision, 2026-10-19:** model arguments must never replace private execution bindings, including through open/catchall input or forwarding into another component. Keep one application `inputSchema`; do not add a second author-maintained input/ownership schema. Trusted code forwards dependencies through configuration and trusted context. The [confirmed private-binding contract](phase2-private-boundary-review.md#confirmed-authoring-boundary-and-recommendation) protects actual own private fields and supported declared private names on schema-backed ordinary and tool paths. Type-only/undeclared absent names are an accepted authoring limitation. The explicit-public-declaration direction is retained, and caller protection for registered tools is confirmed. The [resolved decision](#remaining-phase-2-decisions) adds no blanket private-override opt-out; final security runtime/type integration is not proven by the earlier feasibility checks.
- `inputSchema` controls application validation, stripping, passthrough, and transformations. Retain parsed values and configured public-default resolution. Native schema acceptance alone does not authorize replacement of a private binding. Preserve ordinary extra-field behavior where it does not conflict with the private-collision check in the authoritative preparation pipeline.
- **Confirmed closed-shape type policy:** reject undeclared fields in typed calls for both strict and stripping closed object shapes; preserve native extra-field types for open/catchall shapes. Zod 4 erases the strict/strip distinction from its public TypeScript type. Runtime application parsing retains native behavior, subject to the revised private-data boundary. Check closed union branches against effective merged input: fields retained from another configured branch can make a discriminator-changing call invalid. See the [public proof](phase2-public-api-proof.md).
- Application arguments follow `inputSchema`; explicitly supported source/history forms and named execution options, such as `.run()`'s `abortSignal` and `toolsContext`, keep their separate contracts. Application fields do not become execution controls. Model function-call transport uses JSON, but ordinary JavaScript and coded calls have no additional JSON-only restriction beyond their schema. Include no-schema ordinary calls in private-forwarding tests: protecting configured names changes today's freely overrideable configured-default behavior.
- Preserve the distinction between public arguments and trusted dependencies through every forwarding path. Trusted code can supply private dependencies through configuration/tool context; argument data must not acquire that authority merely by passing through a coded component. Apply the same private-collision rule to schema-backed ordinary calls and tools; without a schema there are no explicit public declarations, so the private-by-default direction protects configured names while allowing unrelated ordinary arguments. A blanket opt-out has not been adopted. Do not add provenance tracking or a second input schema.
- Configured declared input values and schema defaults can satisfy required fields on every entry path. Merge configured application values with call/model arguments before the single parse. Advertise only the model arguments still required; do not require a model to resupply a configured value.
- Every component applies its declared schema at its own boundary and uses the parsed result: inputs, trusted context, outputs, and stream elements. Reuse SDK/Cascada parsing for that same boundary; a new component's declared schema remains a distinct boundary, even when it forwards an already parsed value or stream.
- Keep the shorthand caller usable with valid application inputs. Any required execution setting it cannot supply must be configured, directly or through inheritance; `.run()` overrides settings on an already usable component rather than rescuing incomplete final configuration.
- Remove the generic schema-guided copy planner. Casai's own preparation and execution leave caller context, nested application data, configured values, and shared schema defaults unchanged. Rely on verified native parser behavior and pure callback contracts; unchanged references may remain shared. Native SDK/Zod `.readonly()` freezing, including borrowed/default values and invalid-input cases, is an accepted limitation. Do not add schema rejection, copying, or freeze-prevention machinery to compensate for behavior also present in native Agent.

### Phase 1 Completion

Implemented and covered by [result augmentation tests](../tests/ResultAugmentation.unit.test.ts), public factory/history regressions, and [inference checks](../tests/type-safety/result-augmentation.ts). The [input-resolution correction](#merged-input-correction) remains a handoff to Phase 2. These checks establish:

- SDK Agent assignability and UI-helper interoperability for literal conversations.
- Genuine incremental `streamText` and direct `generateText`, with one execution and native results, callbacks, tool context, and cancellation.
- Coexistence of SDK event/text views and final-result promises, including different access orders.
- Required risk probes: implement a small internal final-output projection/collector, additive result properties, and lazy history over genuine SDK results. Verify intermediate text/array output versus final output, custom output parsers, and every row of the [output-eligibility table](#output-availability-and-failures) in both SDK modes. Include resolved provider tools with same-step answers, unresolved approvals/client/deferred tools, truncated and empty output, final parsing failure, and a completed step followed by a failed continuation. Distinguish failure inside a returned stream from the accepted native continuation-setup limitation below. Interleave native stream views, final-result promises, the candidate final-output view, and lazy history; preserve SDK receivers/teeing and execute once. These focused proofs do not require the complete public Phase 3 adapter.
- Forward native SDK cancellation and complete timeout settings unchanged, preserve failure reasons, and retain completed results after a late abort. Add no Casai timer, cancellation race, or preparation-abandonment layer.

Retain useful core code and regression tests. Discard experimental adapters that do not serve the final design. Register lasting mock-only files in `test:local`; run focused checks and keep the existing checks green. Use mock models for public result integration and SDK behavior tests; do not add paid calls or compatibility-only test paths.

The text implementation adds lazy, non-enumerable `value` and `messageHistory` properties directly to genuine SDK results. Copying with spread or `Object.assign`, and JSON serialization, must not invoke these getters or start consuming the stream. Test paused generation and failed streaming results, including unhandled rejections. It creates no facade, extra execution, eager consumer branch, or output validation pass. Default text can be delivered incrementally after effective step settings establish finality under the provider's declared protocol. Text blocks must also preserve SDK content order: when blocks overlap, stop emitting after the stable prefix and reuse the remaining suffix of the final SDK output, without maintaining another text buffer. Explicit output specifications, including `Output.text()` and `Output.array({ element })`, retries, and experimental tool callers use the final parsed SDK output; text and array values retain iterable delivery after completion. This conservative fallback preserves custom parsing and the collection invariant. SDK stream transforms such as `smoothStream` and text rewriting feed both the stream views and final output; their presence alone does not require this fallback. Native event, text, partial-output, and element views remain available with their SDK contracts.

The SDK owns cancellation, timeout timers, and cleanup. Casai observes native completion failures for `value` without adding a cleanup transform or separate execution scope. Native completion promises own abort/timeout/thrown-stream rejection; one completion check rejects an error in either the native overall or final-step finish reason, retaining the cause from that model attempt when available. If native completion rejects with a cause-less `NoOutputGeneratedError`, reuse the error already captured from that attempt when present. Preserve other native rejections and errors with their own cause. Do not duplicate these paths with abort/finish chunk failure flags. `messageHistory` assembles the SDK's `responseMessages` whenever they are available and preserves their native rejection, without a separate execution-success check. Preserve the [native continuation-setup limitation](#output-availability-and-failures); an error event alone is not proof that SDK completion failed. History availability, execution success, and output eligibility are separate: history may include partial or earlier messages after failure and is not proof of a safe continuation. Tests exercise original abort/error reasons, retry-attempt error isolation, early consumer closure, and late aborts after completion. The augmentation module is shared by all four current LLM factories and the future LLMAgent; native Cascada stream kinds and shared deadlines belong to their later integration phases.

ObjectGenerator and ObjectStreamer add only a lazy, non-enumerable `value` alias for native `object`, including complete arrays and schema-free JSON. Generation returns the parsed value; streaming returns the same completion promise as `object`. Unlike `streamText`, the installed `streamObject` does not drain its stream when a final promise is awaited, and its stream getters share one consumable source. Preserve that contract: callers consume a native stream to drive completion. Add no hidden consumer, tee/replay layer, array collector, or second validation pass. The object APIs provide no generated messages, so do not reconstruct history from parsed output; defer object history until LLMAgent replaces these factories.

### Transition and Check Discipline

Phase 1 integrates result augmentation into all four existing LLM factory paths now: top-level `value`, text-result `messageHistory`, native SDK response fields and callbacks, and no legacy augmentation module. Preserve their current call conventions, synchronous plain streaming, configuration merging, and exclusion of configured static messages from dynamic history. The augmentation accepts an explicit conversation prefix so preparation can retain that distinction. Every literal or prepared prompt string, including `''`, contributes a user message whether history is absent, empty, or nonempty. An absent prompt contributes no message. Resource names are passed to the loader unchanged, including an empty name; the loaded/prepared value follows the same prompt rule. Update callers and tests with each intentional contract correction.

The TextGenerator `.asTool` executor returns final parsed `value`, with its output type inferred from the final merged output setting, including inherited and optional settings. An unavailable nested answer becomes an SDK tool error rather than a successful commentary result. Reuse the SDK's parsed value without another parse or model call; the SDK converts tool output for the model. An LLM tool must reach final output within its own execution. An inner approval, client tool without `execute`, or deferred provider result can pause that execution; the adapter then returns an SDK tool error and does not expose the inner history/approval as outer continuation state. Do not ban such configurations, since automatic approval or an untaken tool path can still finish normally. **Configured defaults and caller permissions are different questions.** Configuration is not automatically public input. Explicitly declaring a dependency as public changes its ownership; Casai cannot infer authorization meaning from a name such as `userId`. Never infer ownership from JSON serializability.

Calls with omitted/empty arguments can therefore use configured public defaults. Preserve shallow public merge laws and explicit `undefined`: an omitted public field retains its configured value; a supplied `undefined` replaces it before parsing and can trigger a default, remain optional, or fail. A present private binding remains private even when its value is `undefined` or `null`. Absent optional private names cannot generally be recovered from runtime values or erased types. No-schema ordinary components protect configured names on every call, including when model data is forwarded to them; new unrelated names remain ordinary input. Test the migration from today's configured-default overrides explicitly.

Private-collision diagnostics name rejected keys without disclosing configured values. Protected key names are therefore not confidential; document that authors must not put secrets in names. Reject a retained private collision even when its supplied value equals the trusted value, including `undefined`; an equality exemption would introduce a value-guessing channel.

**Configured fallbacks receive input validation, confirmed:** when a caller omits a schema-declared field, its configured value participates in the same complete-input parse. The original parser owns application validation; the confirmed private-data invariant is enforced at the separate collision boundary. Selecting configured application defaults keeps unrelated configuration outside this parser; it is not a caller-field admission policy.

**Implemented runtime correction:** the former `validateCallInput`/`validateInput` path validated the caller fragment and discarded successful parsed values; the engines merged configured context afterward. The shared preparation fix changes the placement of merging relative to validation and carries the parsed result through execution, rather than merely reversing an object spread. Preserve the established shallow precedence and prevent downstream engines/preparers from restoring raw values removed by parsing. The SDK integration task below is separate because its native argument-validation boundary does not receive tool context.

**JSON is a transport constraint, not a universal application-input constraint.** Model-generated function arguments use the SDK's JSON protocol. **A child's schema does not limit the parent configuration.** Extra inherited dependencies remain available even when the child's input schema is strict. Fixed/inherited dependencies use ordinary inferred configuration types. Optional `toolContextSchema` validates a different input channel; it does not validate configured bindings on ordinary calls.

**Invocation context is input, not stored state.** In the optional `toolsContext` design, the application calling an owning workflow supplies that map as an explicit execution setting, for example `workflow.run({ context: { value: 2 }, toolsContext: { scale: { factor: 5 } } })`. Concurrent calls capture their own effective maps. No tool-produced value is automatically saved or fed into later calls. The term "private" distinguishes the application-supplied channel from model-supplied arguments; it does not imply persistent memory. Coded callers can provide both channels, while a model supplies only the public arguments. Keep invocation bindings, caller-owned data, and deliberately mutable application state distinct. 3. Apply the original parser once to complete application input and use its returned object. Do not trial-parse fragments or discard replacements.
4. Reject any retained parsed application key in `K`, including a key introduced by a transform. Stripped extras remain stripped; strict rejection remains native; unrelated retained extras remain accepted. Do not silently restore private values over conflicting public data. Report offending argument keys without including private values.
5. Assemble remaining configured bindings and accepted parsed application input in a fresh execution context. Never restore raw declared defaults removed by parsing. Inject actual `_toolOptions` and eligible fallback wrappers, then enter prepared execution. Engines/preparers neither merge raw context again nor reparse input. The confirmed registered-tool-name protection applies before fallback injection; configured/trusted or explicitly public same-name data may still shadow a wrapper.

The registered Casai-tool pipeline is:

1. Resolve the owner's final tool registry and `toolsContext` map, including whole-entry overrides/removal. Capture each selected raw entry and create an immutable binding containing a native descriptor plus its matching raw context. Resolve any owner `prepareCall` changes before binding for SDK dispatch. Plain native tools retain their own descriptors/protocol. Reuse a Casai binding for injected calls and SDK registration that share those effective settings; do not retain a current-run binding on the shared component.
2. Return the descriptor synchronously. Its lazy preparation parses the captured incoming context with the original `toolContextSchema`, if present, and resolves input declarations when sources or private names need classification. Source-free validation must not acquire an otherwise unnecessary declaration requirement. Preserve `undefined` versus `{}` and schema-produced defaults/transforms. This is effective-context validation, not a trial parse. It may fail when an advertised tool is prepared even if that tool is not ultimately selected.
3. Select named raw-input fields from configuration and parsed incoming context. Context overrides configuration, including own `undefined`; other fields remain private bindings. Keep these selected defaults fixed for the binding. Its metadata and validator await the same preparation promise. No metadata-time application default-factory result becomes invocation state.
4. Merge selected defaults with raw tool arguments and apply the original application parser at the SDK/injected argument boundary. Its returned object is public SDK input. Schema parsing does not grant permission to replace private bindings; reject retained parsed keys in `K` before returning successful public arguments, including collisions created by transforms. Parsed context values selected as defaults must be valid raw application input unless repaired by an overriding argument; do not apply the application parser to fragments in advance.
5. Keep the original native `contextSchema` and callbacks on the descriptor, and pass its matching raw context through the native context channel. Native stages independently parse it. The executor combines configured private bindings, incoming private fields from native parsed context, and parsed public arguments. Exclude declared raw names from these binding sources so removed/renamed application defaults are not restored. Before merging, repeat the private-collision check against final public input and actual parsed private context, including supported reserved names. Native refinement/history paths can supply input after fresh validation; this check does not repeat the application parse. Inject actual `_toolOptions` last and enter prepared execution without another public call or application parse.

**Binding lifetime:** all bound context, public and private, stays fixed across tool calls and SDK steps. New independent invocations may construct new bindings with different input; neither the component nor an existing binding changes. Keep borrowed nested/opaque values read-only under the established purity contract, without a deep-copy/freeze planner. Native `prepareStep` can replace context but cannot replace tools; changing an existing Casai binding's context through that hook is unsupported. Preserve that native capability for plain SDK tools. Do not add per-step rebinding, mutable schema state, or a tracking/controller layer. Settings used by a preparer and by model dispatch must each have the binding matching that selected context; if `prepareCall` changes the selection after preparation, create the dispatch binding from its final settings. Context helpers captured before the hook keep their original bindings through every step; they do not become live aliases for the model's changed registry. Reuse the existing prepared registry when the hook retains the selected `tools` and `toolsContext` objects, rather than binding or running Casai's preparatory context parse again. Changed unbound selections get their own dispatch binding; explicitly bound descriptors still require their matching raw context under the mismatch rule below. Preserve independent native SDK validation stages.

**Binding mismatch contract:** an explicitly bound descriptor must retain its matching captured raw entry; replacing it can silently retain incorrect public defaults. Casai-owned settings/hook boundaries reject replacement before native step processing, while plain native tool entries retain native behavior. Accept the same value or, for plain-object entries, the same own keys with `Object.is`-equal values; nested values compare by identity, without deep comparison or reparsing. The [public proof](phase2-public-api-proof.md) demonstrates this owner check. External native SDK consumers own immutable pairing. Distinguish a bare descriptor: accepted private-only native context is valid under 2B; incoming public defaults require explicit binding and fail before body execution, possibly after approval. Do not restore the obsolete blanket prohibition on bare incoming context or promise a universal executor-only binding detector.

Private data is scoped to its component and explicitly selected context entry. An injected child does not inherit the caller body's private fields or another registered tool's context merely because it shares an owner; intentional forwarding uses its configuration or selected trusted context. Test this separately from replacement attacks. For bare SDK tools without discoverable context declarations, the final guard must also check actual native parsed private fields: an empty preparation-time reservation set is not permission to omit that check. Include opaque context transforms, unrelated valid extras and post-parse input changes.

#### SDK Tool Boundary and Configured Defaults

**Binding integration design:** preserve the confirmed input contract through the [registered-tool pipeline](#context-sources-and-preparation). Immutable binding replaces the earlier single shared descriptor for all contexts. The production shared execution path implements binding, its public types and the bounded projector; preserve their paired runtime/type acceptance checks below. Plain native tools are unaffected. Casai components themselves are tool descriptors. Spreading a component into a plain descriptor is unsupported: create a component with configuration and an optional parent instead. Casai registry admission rejects spread copies at runtime and in public types; native SDK consumers own any deliberate type erasure outside Casai.

This complexity buys a specific feature: application-owned incoming context can supply declared public defaults that caller arguments override. It costs a descriptor/context pair per binding, a preparatory context parse, earlier context failures, fixed context within a run, and an explicit integration step for direct SDK users. Forbidding declared-name overlap would permit a simpler fixed descriptor but reverse the confirmed source contract; that alternative is not adopted. A context value matching an input declaration is deliberately public, including approval/history records. Other configured/context values remain outside SDK arguments. Structural separation exists through source selection and parsing; flattening the final execution context does not infer provenance from an argument marker. Public overrides follow the input schema; private replacement remains prohibited.

The SDK automatically applies a registered tool's schema and records its returned value as public tool-call `input`. Install one stable SDK wrapper per binding; its metadata and validator await the same preparation. Every Casai tool needs this wrapper to enforce declared raw keys before native parsing, even with no configured dependencies or defaults. Known private names also require the post-parse collision check before successful arguments reach SDK completed-input hooks/approval. When no public defaults are found, expose the original JSON metadata and delegate accepted input to native validation, without an additional projection restriction or application parse. Keep `.config.inputSchema` as the original schema.

Configured and bound-context public defaults participate in the original application parser without a second author schema or validation of the whole configuration. Unrelated configured/context bindings remain outside the returned public object. Open-schema acceptance cannot authorize a private collision; apply the settled security boundary in every consumer. The executor consumes parsed arguments without repeating transforms. Binding-local preparation may retain its fixed selected defaults; never store a mutable current context on a shared component, descriptor, or original schema. Metadata-time application default-factory results must not become invocation state. Metadata-first and validation-first access share one descriptor and preparation promise.

Derive the registered model-facing object schema from the original input schema without mutating it. Retain declared fields so callers can override defaults; remove a root `required` entry when the selected configured-plus-bound-context default supplies a non-`undefined` value. Preserve schema defaults/optional requirements and constraints. Keep private keys/values out of advertised metadata. The descriptor owns the derived schema and merge-aware validator; `.config.inputSchema` stays unchanged. Use the supported projection below or report a configuration error. Do not hand-write a replacement validator or trial-parse fragments to discover ownership, requiredness, or accepted defaults. Native SDK/Zod metadata conversion may evaluate pure default factories; preserve that behavior. The final merged application parse remains authoritative, including when caller arguments repair invalid application defaults. Never cache metadata-time application default-factory results into component or binding context. The separate real context parse during binding can apply context-schema defaults normally.

**Advertised configured defaults (selected follow-up 7):** add a JSON Schema `default` annotation for a declared public field only when its effective fallback comes from configuration. Use the raw configured value; never annotate private fields or per-binding incoming context values. If incoming context overrides a configured field, omit its configuration annotation rather than advertise the wrong fallback. Do not serialize opaque values, invoke getters/`toJSON`/callbacks to manufacture metadata, or evaluate the application parser for this purpose. Annotate only faithfully representable JSON data on supported object-valued property schemas; skip non-JSON values and boolean/reference schemas. A supplied configuration annotation replaces a native schema-default annotation because configuration participates before schema defaults. This is an annotation-only exception to preserving property schemas, not a validation/default cache or a provider-enforcement promise. The resolved public configuration may already appear in argument records; this additionally publishes supported values in the tool definition, so test exclusion of private sentinels. Prove metadata, default-origin and validation behavior together before integration.

For example, with `inputSchema: z.object({ language: z.string() })` and configured `context: { language: 'English', db }`, model arguments `{}` parse as `{ language: 'English' }`, and `{ language: 'French' }` override the configured input. The execution context also contains the configured `db`; SDK history/UI/next-step messages do not. `language` is a declared public input and its resolved value may appear in SDK tool-call records. Private data belongs in dependency/trusted bindings, not a model-facing schema field. Adding a configured key to `inputSchema` makes its resolved value public, including tool records, UI history, and subsequent model requests.

Keep projection small: support independent object-root requirements using `type`, `properties`, `required`, and `additionalProperties`; annotations `description`, `title`, `$id`, `$comment`, `default`, `examples`, `readOnly`, `writeOnly`, and `deprecated`; and native `$schema` / `$defs` / `definitions` metadata. Reject unsupported root validation keywords when configured or bound-context input merging needs projection, rather than building a general schema rewriter. This includes root unions/composition/references, property-count constraints, dependent requirements, and conditional constraints. Preserve nested property schemas unchanged except for the configuration-default annotation described above. With `minProperties: 2` and configured `a`, raw `{ b }` can be valid after merging but invalid against the unmodified root constraint, even when `a` was already optional and no `required` entry changes. Do not skip the projection check merely because the required list is unchanged, retain such constraints blindly, or silently drop them. Report unsupported projection before execution/provider dispatch, at creation where metadata is available or first use otherwise. The restriction applies only when Casai actually projects a tool schema; unchanged native schemas and unrelated direct calls retain their native support.

When projection removes any root `required` entry, reject `$ref` anywhere in the schema structure, including nested properties and definitions. A recursive child reference to `#` would otherwise inherit the relaxed root requirements even though configured defaults merge only at the root. This conservative rule also excludes safe nested references in that case; do not add reference resolution or rewriting to distinguish them. Inspect only schema-valued positions: an object containing a literal `$ref` under `const`, `enum`, `default`, or `examples` is data, not a schema reference. If the root required list is unchanged, nested references remain supported subject to the existing root-keyword restrictions; schemas needing no projection retain native support. Report a rejected projection before provider dispatch or implementation execution, using the metadata-availability timing above.

**Provider strict-mode constraint, including Casai projection:** [OpenAI strict function schemas](https://developers.openai.com/api/docs/guides/function-calling#strict-mode) require every property to be required. Casai's configured-default projection removes required entries while retaining overrideable properties, so it can make an originally strict-compatible schema incompatible with `strict: true`. Native optional/Zod-default schemas have the same resulting constraint, but the configured-default case is introduced by Casai. The installed provider adapter does not repair it. Preserve the chosen provider setting and document that omission-based configured defaults require a compatible non-strict tool mode. Do not silently disable strict mode, hide overrideable fields, add nullable sentinels, or reject the configuration in a separate Casai policy. An incompatible strict request retains the provider's error. Hiding a defaulted field would remove the confirmed model-override capability and is a different API decision.

A configured value makes an advertised argument omittable; this does not certify that the value passes the original parser. If an invalid configured placeholder is not overridden, the final merged invocation fails validation even when the model omitted that field. Keep this failure at the invocation boundary; do not trial-parse incomplete configuration at creation or weaken the schema to make it succeed.

The native mock demonstrates omitted and explicit-equal arguments, configured/context/schema defaults, root transforms, one fresh application parse, and private dependency exclusion from history and subsequent requests. Each explicit binding owns one descriptor and matching raw context, reused by its SDK and injected calls. A new run may create a new binding without changing the component. **Accepted bare-tool revision (2B):** a bare `.asTool` descriptor accepts native private-only `toolsContext` and must not parse absent incoming context during metadata preparation. Preserve native context-schema identity and validation. Incoming parsed context containing named public-input defaults requires `bindToolContext(rawContext)` and registration of both returned values; report misuse before the component body, potentially after SDK approval. Bare context cannot retroactively affect argument validation. Check actual private context before execution. Casai owners can bind internally from retained definitions. Do not rebuild descriptors per tool call or mutate shared definitions. See the [investigation](phase2-private-boundary-review.md) and [signature gate](#schema-capability-and-public-signature-gate).

The no-redundant-parsing rule applies to application input and unnecessary Casai work, not the SDK's total context-validation count. Binding has one preparatory context parse to select public defaults before native argument parsing; native hooks, approval, and execution retain their independent context parses and errors. The prototype observes one binding parse plus three native parses with all three stages enabled. Do not reuse binding's parsed context to suppress native SDK validation, wrap the original context schema, or synthesize hooks to equalize SDK/injected counts. Casai injected calls instead reuse the context already parsed during immutable binding preparation (selected follow-up 6); schema-produced objects are consequently shared within that binding and remain read-only under the purity contract. Plain native tools without a Casai binding retain per-call context parsing. Invalid binding context can fail during lazy preparation before provider dispatch, including for an advertised but uncalled tool.

Keep parsed execution context separate from conversation persistence. Casai assembles that context for the invocation; SDK tool records contain the parsed public application arguments, not the flat context with private dependencies/trusted bindings. History is assembled from messages and SDK response messages, not by serializing execution context. "Parse once" here excludes redundant parsing inside Casai's execution wrapper; it does not prohibit native SDK validation of historical UI messages or approvals on later requests.

**Approval configuration stability:** native continuation revalidates recorded raw `inputSchemaInput` when present and requires its parsed public value to equal approved input. Changing a configured or bound-context default used by those arguments can produce an SDK `InvalidToolInputError` tool result without executing; the model call may continue. Keep effective public input stable across continuation. A new binding with unchanged public defaults and different private dependencies succeeds. A changed default also succeeds when an explicit recorded argument overrides it and keeps parsed input identical. These are separate immutable bindings, not context changes within one binding. Preserve native revalidation and add no history rewriting, snapshot store, or approval workaround.

**SDK UI helpers read exposed tools before invocation:** `createAgentUIStream` validates UI history against `agent.tools` before calling `agent.stream`, so before `prepareCall` can select another binding. An approval recording `{ factor: 5 }` from raw `{}` fails when exposed tools supply fallback `3`, even if `prepareCall` would select `5`. A native SDK default-only comparison reproduces this; a matching exposed binding successfully executes. Phase 2's binding API must support an immutable registry available before helper entry, and Phase 3's Agent integration must expose it through `tools`. Configure a request-specific agent with the matching public defaults when needed. Selecting dispatch tools inside `prepareCall` alone does not satisfy UI approval compatibility. Preserve native validation and its pre-invocation rejection, without mutating shared `agent.tools`, rewriting history, or bypassing the helper. Include this consumer in the binding/signature gate; ordinary model-message continuations use their separate native boundary.

**Accepted native SDK UI round-trip limitation:** a local probe using unmodified `ToolLoopAgent` in `ai@7.0.130`, with `z.object({ n: z.string().transform(Number) })`, executed `{ n: "3" }` as `{ n: 3 }` and recorded the parsed input in UI history. A second `createAgentUIStream` call rejected that historical number against the string-input schema before invoking the agent. Direct `.generate()` and `.stream()` continuations using completed SDK model-message history succeeded; those paths did not reparse the completed historical tool arguments. Private `toolsContext` data stayed outside both histories. The SDK carries raw `inputSchemaInput` for relevant approval records, but ordinary completed UI tool parts do not have that same raw-input path. Casai accepts this native SDK behavior without a workaround or additional schema restriction; fixing it is not a phase-completion requirement. Keep focused comparisons with native Agent behavior, including approval continuations, and recheck on SDK upgrades rather than requiring the current failure forever. A possible upstream bug report is separate follow-up work.

See the [source preparation table](#context-sources-and-preparation) for schema owners on every entry path. Explicit SDK tools and `Output` objects keep their native schema interfaces/results; Casai projects only its own component tools when declared configured inputs need merging.

#### Schema Capability and Public Signature Gate

**Production schema/signature acceptance criteria:** the [combined proof](phase2-composed-api-proof.md) established bounded feasibility before integration. The production factories now compose those guards with inherited implementation/schema compatibility. Preserve the following acceptance criteria when changing them; the [review ledger](phase2-review.md) records current evidence and remaining gates.

- Keep the proven schema-capability matrix for no configured sources, configured defaults, unrelated private configuration, and bound context. Pair actual schema instances with runtime and factory/call type checks, including root unions, Zod 4 Classic/Mini intersections, preprocessors, lazy/opaque schemas, wrappers, and explicit native metadata. Do not equate structural types with runtime constructors. Reject known unsupported combinations and check dynamic metadata at preparation. Native-protocol authoring must retain raw/output types; declaration-only union examples must not be presented as faithful projected model schemas.
- Compute declaration demand from every consumer, not only configured values. Supported private-context declarations and executable fallback registries also require application-name discovery, even when `config.context` is empty. Factory/admission types must carry those triggers through inherited registries and binding; otherwise a known unsupported input schema can compile and fail on every ordinary call. A description-only registry creates no executable reservation, a removed entry creates none, and an opaque context schema is not parsed on an ordinary call merely to discover names. Preserve those valid source-free cases and the explicit-metadata escape hatch. Keep this bounded output-declaration typing distinct from raw context types and broader retained private-key types; do not add callback probing or a general schema interpreter. Pair each trigger's runtime behavior with a separate compiler negative and valid neighbor.
- Use schema-shaped public argument types for completion, contextual typing, and useful missing/wrong-field diagnostics; layer a merge-validity constraint only where necessary. Prove ordinary calls, omitted arguments, `.run({ context })`, injected bindings, external binding, inherited configuration, and parsed callback/result types against the same admitted schema cases. Retain raw schema types and both exact-optional modes. A simple partial-by-key type is a candidate for independent object fields, not permission to weaken the confirmed union/optional override guarantees.
- Keep structural union-assignability examples as algebraic tests until corresponding runtime capability is demonstrated. A union of all branch names can select a configured field forbidden by the active strict branch; it is not a general branch-selection solution. Do not add trial parsing, silently drop configured defaults, or publish all configuration to bypass discovery.
- Compile production signatures with TS7 against source and emitted declarations; retain the proof's completion/contextual-inference checks and both exact-optional modes. Include valid neighbors for rejected capabilities and preserve parsed output typing. Carry the explicit descriptor/raw-context binding contract below into every tool form and the registry exposed before UI-helper entry. Full projection, factory-specific source overloads, errors, stream integration, and the subsequent complete review remain implementation obligations.
- Cross output schemas with inline callbacks that read parsed input and configured/inherited private dependencies, including async and no-input-schema producers. A separate return-type check must not prematurely reject an uninferred return type as `unknown`; constrain producer returns to raw output-schema input while retaining parsed result types and rejecting wrong producer values. Carry registered-tool alternatives through helper inference without collapsing distinct definitions into an impossible shared schema. Test usable common calls, output unions, private-key negatives and editor completion against source and emitted declarations.
- Name rejected keys in diagnostics. When the closed-shape rule rejects an undeclared field, the compiler error must identify that field (for example, `requestId`), not only a guard property such as "Effective input must satisfy the schema shape". Cover literal and non-literal arguments.
- Budget type-check cost. Production signatures add these checks to factory types that are already expensive: on 2026-10-18, `tests/type-safety/result-augmentation.ts` alone measured about 4.0M instantiations, 22 s check time, and 1 GB with TypeScript 7, while the isolated candidate measured 0.38M instantiations and 1.1 s. Record `--extendedDiagnostics` instantiations and check time for representative factory type tests before and after integration with the supported TS7 compiler. Treat a large regression, an "excessively deep" instantiation error, or degraded editor completion as a signature-design defect.

**Binding API established by the proof:** tool forms expose `bindToolContext(rawContext)`, returning a fresh readonly pair `{ tool, context }`. `tool` retains native parsed-input/output/context types and original `contextSchema`; `context` is honestly typed raw input. Do not override a callable's native JavaScript `.bind`. A bare component supports private-only native context without binding; external consumers supplying public defaults through context must register the explicit matching pair. Preserve absent `undefined`, scalar-to-object context transforms, and opaque instances; snapshot plain maps without converting class instances into maps. No-schema bindings retain supplied context types, with compatible replacement dependency types for the fixed implementation. For transforming context schemas, the SDK still infers parsed context settings and can require a narrow native type assertion; never label raw data as parsed to hide that limitation. Casai dispatch owns its internal SDK bridge. The proof's `invoke` and registry assembler are internal candidates, not additional public package methods. A bound `tool` is a plain native descriptor without `.config`: a Casai owner that receives it in `tools` treats it as a native tool and does not rebind it, so the owner's `toolsContext` entry must be the pair's `context`. Use the component, not its bound descriptor, as a configuration parent.

Casai owners assemble fixed bindings before SDK/UI entry and reject hook results changing their selected entries before native dispatch; untouched explicit native tools keep native context replacement semantics. Arbitrary external SDK consumers own matching and immutable pairing. Do not promise universal descriptor-side mismatch detection: the argument validator cannot see native execution context, and execute-time checks are too late for earlier hooks/approval. Phase 3 exposes the matching immutable registry through `Agent.tools` before `createAgentUIStream` validates history.

#### Native Parsing, Purity, and Types

Schema admission must match the promised object-in/object-out contract, not a concrete constructor. The former `validateRendererInputSchema` and `ValidateRendererInput` rejected an object followed by a root transform and did not admit all installed Zod 4 Classic/Mini forms used by this plan. Shared preparation now replaces those gates across the factories; preserve transformed-schema support outside Function too. Retain discoverable raw declarations where configured defaults require them, and validate the resulting object shape at the preparation boundary. Use the native asynchronous parser for checks/transforms on every input/output boundary. Do not execute validators at construction to discover their output shape or require JSON conversion merely to validate a local input. Custom/erased schemas still receive the normal invocation-time checks.

Distinguish omitted raw arguments from parsed replacements: an omitted ordinary argument starts as `{}`, but an application parser returning `undefined`, `null`, an array or a scalar fails the object-context boundary before body entry. Do not reuse optional-tool-context normalization to turn a parsed `undefined` into `{}`. Reject schemas whose retained output type guarantees no object; optional wrappers may remain usable when the actual completed-input parse returns an object. Absent incoming tool context retains its separate native contract. Pair these cases on ordinary, `.run()`, injected and SDK argument-validation paths; compare the native parser's actual replacement with Casai's subsequent object-context check.

Casai supports Zod 4 Classic/Mini, SDK schemas and Standard Schema. Reject directly supplied Zod 3 component input/output/tool-context and stream-element schemas in types and at runtime, including ObjectGenerator/ObjectStreamer `schema`. Native third-party tools and SDK output specifications such as `output: Output.object({ schema })` retain SDK support without Casai inspecting their internals. This confirmed decision includes the retiring Object factories and supersedes Zod 3 acceptance in the historical proofs.

Normalize supported schemas through the SDK's public `asSchema`/validation contract rather than branching only on `.safeParse` or `.validate`. Align `SchemaType` and inference with installed `FlexibleSchema` forms: Zod 4 Classic/Mini, SDK schemas, lazy SDK schemas, and Standard Schema. Retain precise raw types when their declared schema types expose them; erased SDK schemas retain their native limitations. This reuses native schema handling, not a new parser family. Before Phase 2, Lazy and Standard Schema validators fell through Casai's direct input validator without running, although native normalization parsed them. Shared preparation now normalizes both input and output boundaries. Runtime validation support does not imply JSON metadata availability: Standard Schema without a JSON converter can validate locally, while model projection or configured-default discovery still needs the separately specified declaration contract.

Casai's own preparation and execution must not mutate caller context, nested application data, configured values, or shared schema defaults. Installed Zod 4 creates new declared object/array containers on their ordinary structural parsing paths; do not pre-copy those containers again. This is not a copying guarantee for every wrapper or default: Zod 4 object defaults can retain nested references, and a default factory can return an existing object directly. Opaque values, functions, clients, passthrough branches, and default-provided values may remain shared. Preserve native parser behavior, including the accepted freezing cases below.

Custom validators, refinements, preprocessors, transforms, and default/catch factories MUST be pure: do not change received/shared data or perform external effects. A transform that changes an object or array returns a new one and copies each nested path it changes; unchanged branches may be shared. For example, return `{ ...value, profile: { ...value.profile, name: value.profile.name.trim() } }` rather than assigning to `value.profile.name`. Return a fresh structured default when it should be independently owned, including any nested objects that will be affected. Component implementations have the same no-mutation obligation for their input data; intentional external operations belong in execution, not schema callbacks.

**Accepted native freezing behavior:** `.readonly()` freezes the parser's returned value. A successful structural parse ordinarily freezes a new container, but opaque values and objects supplied by default/catch factories or pure transforms can retain shared identity. In installed Zod 4.6.5, even `z.string().readonly().safeParse(sharedObject)` freezes the invalid object; a failed union branch can likewise freeze a value before another branch succeeds. A shallow context merge does not protect a nested borrowed value. These behaviors are inherited from the parser, not introduced by Casai. Unmodified `ToolLoopAgent.generate()` and `.stream()` in `ai@7.0.130` reproduce borrowed-option freezing, shared-default freezing, and freezing before invalid options are rejected. Accept native SDK/Zod behavior without a Casai rejection layer, copy planner, parser patch, or completion gate. This supersedes the earlier proposal to reject unsafe `.readonly()` combinations. Custom callback purity remains required.

The earlier selective-copy proposal would shallow-copy schema-selected containers and their ancestors before native parsing, sharing unaffected branches; it would not implement validation or transformation. That can protect some borrowed input containers, but duplicates native copying on ordinary structural paths and cannot protect a shared object introduced later by a schema default. Do not restore it to compensate for the accepted native behavior. Focus isolation work on Casai's own merging, source binding, and invocation state.

When a present schema setting explicitly has a `Schema | undefined` type, preserve both possibilities. Calls must satisfy the schema-present input requirements and the no-schema private-binding rules; configured values can still satisfy required input. Bodies and results include the raw and parsed alternatives, including missing schema defaults when parsing is absent. A statically known schema permits its usual public overrides. Optional schema properties in annotated configurations preserve the same possible absence; an annotation cannot guarantee parsing. Preserve property presence through inference and use the ordinary configuration merge: an omitted child setting inherits, while an explicitly undefined setting removes the inherited schema. With exactOptionalPropertyTypes, an optional property excludes an own undefined unless its declared value type includes it. Conditional spreads remain usable without additional annotations. Prove inline callback inference as well as final call validation, through source/emitted declarations and both optional-property modes.

Input/configuration and producer-return types describe schema inputs; implementations and consumers see schema outputs. Infer required public fields remaining after configured defaults and preserve ordinary-component/native-tool open/catchall types rather than synthesizing a named-key-only input. Casai tools follow the closed-root admission rule; opaque types still rely on runtime declaration checks. The implementation type follows ordinary merge precedence: configured bindings, then parsed trusted values if applicable, then parsed application input. No-schema callback-derived signatures must distinguish remaining ordinary arguments from protected configured names; current configured-override inference is not preserved. Prove this together with schema-backed signatures rather than using a permissive-schema stand-in. Model-tool requirements reflect the projected schema. For output/stream schemas, producer types describe raw values and consumer types describe parsed values. Both preparation hooks receive parsed application context. Preserve exact-optional/union behavior without widening to `any` or changing unrelated merge rules.

**Native tool typing limitation:** infer raw input precisely where the original schema type is retained, including Casai component `.config` schemas. An SDK `tool(...)` definition can erase that information: its trusted-context settings are inferred from parsed output, so native types can require a context whose schema defaults missing input, or expect a number where runtime parsing accepts a string transformed into that number. Explicit SDK tools retain these native typing limitations. Do not add schema interpretation, speculative parsing, or recovery machinery to reconstruct erased types; native SDK method/property types remain unchanged. Scope raw/parsed type guarantees and required-context checks to the information available in the declared types.

#### Schema Verification

**Migration rationale:** the former factories validated then discarded parsed input, and used the public `_toolCallOptions` marker to skip validation. Phase 2 removes both behaviors. With stripping schemas, undeclared caller fields disappear before execution; retained private collisions fail. This can change existing Cascada calls even where TypeScript catches typed callers. Document explicitly declaring overrideable configured fields in `inputSchema`, using trusted channels for dependencies, and consuming parsed values. Do not add warnings or errors for ordinary stripping merely to ease migration. For schema-less configured defaults that should remain overrideable, introduce explicit public declarations. To preserve arbitrary unrelated arguments too, use `z.looseObject({ ...publicFields })` in Zod 4: a plain `z.object` would silently strip those extras at runtime. A stripping/strict schema remains appropriate when that change is intentional. With no configured overrides, unrelated arguments alone do not require introducing a schema. Follow the [migration inventory](#configured-override-migration-inventory) across documentation, runtime tests and compiler consumers.

2. Add a callable tool wrapper only if its name is not already an own property of the final prepared execution context. On ordinary non-tool components, a caller-only key stripped by the input schema does not shadow a fallback tool; a strict-schema rejection prevents execution before injection.
3. Never mutate configured context, caller input, tool definitions, or the shared Cascada environment. No global registration or environment inheritance is required.

A deliberately shadowed name keeps the accepted configured/trusted or explicitly public value; calling a non-function fails normally without falling back to the tool. Shadowing affects this convenience binding, not the model's registered tool set. Applications needing both can register the tool under a different name.

Each injected wrapper uses one small common tool-invocation path: normalize named arguments with the [shared Cascada normalizer](#calling-components-from-cascada), removing `__hasKeywordArgs`; parse through the selected bound descriptor's SDK-facing `inputSchema`; obtain the Casai binding's already-parsed fixed context; check the captured signal; then invoke `execute` once with native options. A plain native tool without a Casai binding instead parses its own `contextSchema` from the captured raw entry per call. Preserve that native distinction without caching context on the shared component. Casai descriptors own default merging, private bindings, parsed context assembly, output validation, and root-stream collection; injected callers do not repeat that work or inspect private component configuration. Explicit native tools retain their own schemas/options. Consume a plain SDK executor's preliminary async iterable once and return only its final yield, including native empty-iterable behavior. No validation marker or parallel execution framework is needed.

Infer fallback bindings in Function and `.withFunction` context instead of using `any` or duplicate declarations. A Casai binding accepts raw public input with omissions guaranteed by its selected configuration and context, and returns the completed tool result: collected string/array for declared root streams, final application value for generator tools. Ordinary component call types still use configuration alone, since they have no incoming context. Derive bound omissions from guaranteed parsed tool-context properties compatible with raw application fields; optional/union/undefined cases must not discharge unsupported requirements. Preserve raw context input types when the original schema exposes them. Native SDK `InferToolSetContext` infers parsed output even for transformed context; any necessary native-dispatch bridge stays internal and must not falsely type raw returned values as parsed. Explicit native tools keep erased-type limitations. Definite configured/trusted or explicitly public bindings shadow tool types; optional/union declarations must not falsely promise callable helpers. An unrelated open index signature alone does not authorize shadowing a protected registered name; compose the named-collision check with helper inference. Resolve inheritance, replacement, and removal before inference.

On schema-free Function calls, execution-supplied `_toolOptions` and guaranteed injected helpers must not become required caller fields merely because a callback annotation names them. Other unsatisfied application requirements remain required. The reserved metadata property's implementation type overrides any same-name application type, matching its final runtime injection; do not intersect incompatible property types into `never` or expose it as caller-controlled execution authority.

Helper typing must require a declared key before treating assignability as a guaranteed configured/public shadow. TypeScript's empty object type can satisfy `Record<'toString', unknown>` through inherited Object members even though `toString` is absent from its declared keys; that check alone can incorrectly suppress a callable fallback and infer `never`. Pair prototype-named callable helpers with explicit own shadows and required public fields in source, emitted declarations and editor checks. This corrects the derived guarantee without changing runtime shadowing or trying to recover erased ownership information from arbitrary structural types.

The common injected runner is not a flat-context parser for arbitrary SDK tools. A native tool may accept a scalar, array, or other schema-supported value; pass its single positional input through unchanged. Normalize only a marked Cascada keyword object. Casai-created components retain their object-context contract. Native tools without an executable handler, including provider-only tools, have no local fallback callable; preserve them in a model registry when supported, without synthesizing local execution. A plain native tool with an executable handler keeps its own input/output/context and preliminary-result protocols. Test this independently of Casai component tools.

A plain SDK tool needs an `execute` handler and receives a generated `toolCallId`, an empty `messages` list, its parsed `context`, and the owning invocation's signal when supplied through `.run()` or an SDK tool entry. No model made this call, so approval policies do not apply and no chat tool-call events are manufactured. Consequently, a component exposed as a model tool can invoke an approval-gated tool through its injected wrapper without approval. When the inner effect needs human confirmation, put the approval requirement on the exposed outer tool; Casai does not propagate approval through coded calls. A component explicitly supplied in `context` instead uses its ordinary callable and full result, and shadows an injected tool of the same name.

An incoming outer tool context does not implicitly become an inner registry's `toolsContext`. Explicitly call an existing child component through `.run({ context, toolsContext, abortSignal })` to forward selected dependencies, using a Function bridge or a component available in Script/Template context. This reuses the child and its compiled source while creating an independent binding. The ordinary injected-tool callable accepts only its application input; it has no second per-call context override. Configured child registry defaults remain subject to the shorthand-usability rule. Add no ambient context propagation or mandatory per-request reconstruction to solve explicit nested forwarding.

#### Sharing Environments and Compiled Code

Let Cascada own named-resource acquisition, compilation, and invalidation through its ordinary environment APIs. Preserve source origin, declaring loader, relative imports, `noCache`, reload policies, update events, and template/script mode. Identical source text at different paths can resolve different dependencies, and a named source can change between calls; a Casai cache keyed only by source text/name and mode would lose those semantics. Add no general compilation cache above the engine.

Retain simple per-component compilation for inline source. Building a callable per request from `Config` currently creates another environment and recompiles inline source on first use; named-resource caches also belong to that new environment. State this cost in the request-binding guidance. Sharing compatible parent resources is optional: reuse only compilation/environment resources, with invocation data and configured context kept separate. Do not reuse the existing whole engine with another request's retained configuration. Compatibility depends on loader, filters, `renderOptions`, source origin/mode, and compiled source where relevant. Use native caches, preserve reload/invalidation behavior, and avoid a global environment registry or serialization of opaque identities. An optimization needs a demonstrated benefit and is not a Phase 2 prerequisite.

#### Stream Ownership and Runtime Responsibilities

Casai streams use ordinary consumption. Passing a stream to a component permits that component to consume it. Returning the same source does not rewind it or restore consumed items: it may have unread items, be exhausted, or have been closed. A fresh producer returns a fresh consumable stream. Casai adds no replay cache, cursor registry, or custom concurrent-reader locking policy. Native source contracts still apply.

Cascada's installed engine already shares async iteration within its loops by default. Several loops over the same source can each read the retained sequence; this is engine behavior, not a Casai return-value guarantee. Passing that source to JavaScript or returning it retains native consumption behavior. JavaScript callers can explicitly request sharing through Cascada's `makeSharedIterable`; its `replayAsyncIterables: false` environment option selects native loop consumption. Casai need not disable internal loop sharing to preserve ordinary JavaScript stream consumption.

Native replay also spans separate renders that reuse the same source object; it is not reset at component invocation. A loop may therefore repeat its body for previously consumed values, including external effects in that body. Source owners should provide a fresh source for independent runs, or select native loop consumption with `renderOptions: { replayAsyncIterables: false }` when that behavior is intended. Explicit disposal ends replay permanently for that source; it does not reset it for reuse. Preserve this source-lifetime contract without adding a Casai replay cache or automatic per-run disposal. A focused installed-engine probe returns an untouched iterable without pulling it, then replays its two values in two loops across two renders while pulling the original source only twice.

Cascada owns its shared buffer, cursors, and source lifetime. Closing a shared cursor closes only that reader; render completion does not dispose the source. Explicit disposal belongs to the source owner, including when a stream escapes through a return. Casai forwards cancellation and closure through its adapters according to the underlying contract, without introducing another shared-source manager. Runtime sharing does not copy native properties or Casai stream-kind metadata automatically; integration must retain the declared kind without promising object identity for adapted streams.

| Casai responsibility | Implementation boundary |
| :--- | :--- |
| Choose complete or streaming execution | Call the appropriate SDK or Cascada API; invoke Function producers once |
| Declare stream kind and apply component schemas | Validate healthy values lazily in the consumer's pass; reuse Cascada's native validation |
| Select final LLMAgent output | Adapt SDK results into `value`, buffering candidates only when finality requires it |
| Surface terminal SDK failures through `value` | Preserve raw SDK protocols while rejecting failed Casai output consumption |
| Collect explicit results and finite tool outputs | Use the existing collectors and one producer execution |
| Forward cancellation and cleanup | Pass execution options and propagate iterator closure; runtimes own scheduling and shared-source cleanup |

Cascada owns source-order assembly, poison propagation, and complete-value/native-stream failure. Casai uses the engine contract directly without constructing internal/public consumer views. SDK branching and buffering retain their native contracts. Neither engine behavior nor final-answer buffering creates a general Casai replay promise.

**Explicit web-stream conversion and sharing (selected follow-up 5c):** retain async iterables as the primary stream representation. Export `toReadableStream<T>(source: AsyncIterable<T>): ReadableStream<T>` as a small consumption adapter, plus a direct re-export of Cascada's `makeSharedIterable`. Conversion adds no validation, replay, producer execution or source-wide disposal. Use zero-prefetch pull/backpressure: neither construction nor acquiring a reader advances the producer; a read does. Forward cancellation to the active iterator's `return`, matching the native SDK helper's cancellation behavior. Prefer the small local adapter over an undeclared transitive dependency; it does not require `ReadableStream.from` in browsers.

For two consumers of a single-use source, explicitly wrap the validated stream once with `makeSharedIterable`, then pass that shared view to the converter and the other consumer. Validation occurs before the shared buffer, so each source item is parsed once for that component boundary. The native helper retains history until owner disposal, potentially across renders; cancellation closes only the selected reader and does not dispose the shared source. Document memory/lifetime costs and permanent disposal. Test single-use and re-iterable sources, lazy validation, failure propagation, cancellation during a pending read, independent shared readers, and SDK response-helper compatibility. No automatic Casai replay layer is introduced.

#### Stream Schemas and Collection

Phase 2 defines text and element stream kinds in Casai's JavaScript wrappers, including empty streams; never infer kind by inspecting items. Both are async iterables. Phase 3 reuses these kinds for LLMAgent `value`. Phase 6 maps them to Cascada's native `tstream` and `stream` without changing public schemas or collectors.

- `textStreamSchema()` declares a text stream, corresponding to Cascada `tstream`, and checks string chunks. `collectTextStream()` joins them, returning `''` when empty.
- `streamSchema(elementSchema)` declares an element stream, corresponding to Cascada `stream`, and validates elements lazily. `collectStream()` collects them in order, returning `[]` when empty.

Stream schemas describe only a root stream: a Function's returned stream or, already in Phase 2, a Script's returned JavaScript async iterable. Both use the same lazy schema boundary and finite-tool collection. Native Script `stream`/`tstream` channels and live channel returns join this contract in Phase 6. A JavaScript stream nested in a returned object is an opaque value: Casai doesn't validate its elements, and an output schema that mentions it uses an opaque schema such as `z.custom<AsyncIterable<T>>()`. In Phase 6, Cascada first resolves a native channel assignment to its source-order snapshot; an ordinary output schema then validates the resulting array or string. JavaScript stream references stay opaque and are not recursively drained by that validation or by tool adaptation.

Export both schemas and helpers in Phase 2. A Function or Script returning a plain JavaScript async iterable acquires its declared runtime kind at the schema boundary. Keep the JavaScript representation internal and adapt it to Cascada's runtime protocol in Phase 6, preserving lazy iteration and producer identity. Do not wait for that protocol to implement or test Function producers, Script iterable returns, validators, collectors, and tool adapters.

Try implementing stream schemas through the ordinary SDK `Schema` validation interface, returning the lazy parsed iterable, with minimal declared-kind metadata for collection. Prefer this if it removes a separate parse path. Preserve transformed producer-input and consumer-output inference; SDK `Schema<T>` alone describes only the output type. Keep stream schemas at the component output boundary, not as model-facing JSON stream schemas. The internal representation is an implementation choice, not another public schema family or a requirement to attach metadata to every borrowed stream.

Each component's declared stream schema owns a parsing boundary. Parse its producer elements lazily in the caller's consumption pass and forward the parsed values. Where needed, one wrapper reads one source element, applies that component's schema, and yields its output; collection consumes this parsed view without another pass. Do not read merely to construct a wrapper, start another producer/source reader, or retain replay history. If SDK/Cascada already implements that same component's declared boundary, reuse its parsed output instead of parsing it again. Text schemas check string chunks; element schemas forward healthy parsed elements. A validation failure stops iteration before yielding the failed element, after any valid prefix; whole-stream validity still requires completion.

Preserve the source's iteration contract: wrapping a re-iterable source must not accidentally turn it into one single-use generator. Each requested iterator lazily obtains its own underlying iterator, while a genuinely single-use source stays single-use; Casai neither re-executes the component producer nor promises replay or concurrent-reader safety. No source iterator is acquired by an unread wrapper. Close the active iterator on consumer exit or element-validation failure using ordinary iterator semantics. Wrap Casai element-validation errors as `ValidationError` at the lazy element boundary, preserving the cause; a catch around initial output parsing cannot catch later iteration failures. Producer errors retain their identity. Do not introduce a broader source-disposal guarantee or normalize producer errors into validation errors.

```text
producer -> lazy schema validation -> caller
```

Forwarding into a new Function or Script with its own declared schema is a new component boundary. That schema still applies: an SDK stream of numbers may contain `-1`, which a forwarding Function declared with `streamSchema(z.number().positive())` must reject. Two components each declaring `z.number().transform(n => n + 1)` apply their own transform, so an initial `0` becomes `1` and then `2`. A forwarding adapter or collector with no new declared schema adds no parsing boundary. Use this structural ownership rule rather than a global validated-stream flag, schema-identity deduplication, or provenance cache.

Stream schemas do not promise that the entire result is valid before the first element is delivered. Whole-result checks can only be finalized at completion; guaranteeing complete validity before exposure requires explicit collection. Ordinary streaming adds no such eager pass or buffer.

Callers explicitly choose collection helpers, which also accept plain async iterables and consume them in their current state. Casai collects a finite Function or Script stream for a tool according to its schema kind: text joins into a string; elements collect into an array. A Casai tool's `execute` never returns an async iterable to the SDK. Tool adapters collect only a declared root stream; non-iterable root results, including objects containing streams, are returned as the component produced them, and making them suitable for a tool is the component's job. Collection consumes the validated stream; it does not rerun the producer or repeat that boundary's validation. Cascada channel returns and source-order snapshots join this contract in Phase 6.

This deliberately exposes a completed Casai tool value, not SDK preliminary tool-result updates. Streaming a Function's ordinary result does not stream progress through its `.asTool` execution to a UI. Applications needing the SDK preliminary-result protocol can register an explicit native SDK tool; adding a Casai progress-output API is separate future work, not an implied capability of stream collection.

**Undeclared root iterables:** ordinary Function/Script calls and `.run()` may return a JavaScript async iterable without a stream schema, including one accepted by an opaque ordinary output schema. It retains its ordinary consumption contract and has no declared Casai stream kind. Tool execution instead requires `textStreamSchema()` or `streamSchema(elementSchema)` for an async iterable at the root. After awaiting the producer and applying any declared output schema, reject an undeclared root async iterable with `ConfigError` before acquiring or pulling its iterator; do not guess its kind, collect it implicitly, or hand it to the SDK. Reject `.asTool` statically when the retained output type guarantees this unsupported result; keep the runtime check for Script returns and erased or union-valued outputs. Nested iterables remain opaque under the existing root-only rule. This restriction concerns Casai component tools, not explicit SDK tools.

Preserve the native result-normalization distinction for explicit SDK tools: a directly returned async iterable supplies preliminary results and a final last-yielded value, while the installed SDK treats a promise resolving to an iterable as one final value. Reuse the supported native executor helper or exactly preserve that distinction; an eager `await` before detecting preliminary iteration changes native behavior. Casai's own executor must resolve its output and enforce the declared-stream policy before returning a completed tool result.

#### Function Producer Contract and Types

Use one `execute` callback. A streaming Function returns an async iterable whose kind is declared by `schema`; no mode flag is needed. Its flat context includes validated tool-context fields and the reserved `_toolOptions` property for cancellation and native tool metadata, with no separate options argument.

Every `.withFunction` preparer receives one prepared `context` containing `_toolOptions`, with no separate execution-options argument, including specialized components that prepare audio or other non-text inputs. Forward the invocation signal during preparation; check cancellation before starting the backend, and do not start it after preparation has been cancelled. Before Phase 7, await the preparer normally; do not race it against cancellation or add a timer. This explicit cooperative forwarding does not depend on automatic Cascada propagation.

`textStreamSchema()` requires a (promised) `AsyncIterable<string>`; `streamSchema(elementSchema)` requires a (promised) `AsyncIterable` whose producer element type is accepted by that schema. The public stream yields parsed elements of the schema output type and throws on failure, so consumers need no `T | PoisonError` union. Once Phase 3 is available, a Function can forward an LLMAgent's native output stream, retaining final-output selection, any required buffering, and terminal failures. SDK event and transcription streams remain separate protocols.

Correct the public unschematized Script result type as part of this work: script source can return arbitrary JavaScript values, including an untouched async iterable, so `ScriptResult = JSONValue` is not sound. Use `unknown` when no output schema describes the result; with a schema, expose its parsed output, and with a stream schema expose the parsed iterable or completed tool collection as appropriate. Function without an output schema continues to infer its callback return. Update `ComponentTool`, `toModelOutput`, exported aliases, and declaration tests along with the collectors; do not widen validated stream results to `any`.

#### Calling Components from Cascada

The `greeting` examples below assume `name` is explicitly declared in its `inputSchema`, as in README2's main calling example. Keyword syntax does not grant permission to override an undeclared configured binding.

Phase 2 supplies shared Cascada keyword normalization for coded components and injected tools. Retiring Text/Object factories keep their existing positional calls. Phase 3 establishes LLMAgent's rendered convention: with a configured source, `(context, messageHistory?)`; with a source override, `(source, context, messageHistory?)`. Source types follow the modifier: template/script text, a resource name, or a function preparer. LLMAgent `.withFunction` gains positional history under this order. Context may be omitted only when configuration satisfies its requirements. The new LLMAgent rejects old unmarked history-before-context orders instead of adding compatibility overloads. Its plain prompt/message-array resolution and named `messageHistory` API also belong to Phase 3.

Apply the required-configuration rule to source availability in runtime and types together. Ordinary inline Template/Script and existing rendered LLM forms may leave a source unconfigured only when their existing ordinary caller can supply it. The new function-valued source override belongs to Phase 3 LLMAgent `.withFunction`; its final caller types must then permit that source without a contradictory creation-only requirement. Phase 2 does not add that call form to current factories. Loaded forms still require a loader. Tool forms must have their source configured because tool arguments are application data, not a source override. Keep configured/overridden empty source strings valid. Audit concrete factory requirements against the call surface owned by each phase.

Context inputs use one named object. Cascada accepts object-literal calls such as `multiply({ a: 6, b: 7 })` directly; keyword calls such as `multiply(a=6, b=7)` arrive as `{ a: 6, b: 7, __hasKeywordArgs: true }`. Remove the marker before validation, otherwise `.strict()` schemas reject it and it appears as a template variable, and treat the object as the final input or context argument. Keyword calls then work with each component's positional conventions, such as `greeting('Welcome {{ name }}.', name='Ada')` for a Template's `(template, context)`. A marked keyword object fills the context argument and cannot be combined with a positional context argument. Reject a call that supplies both, such as `fn({ a: 1 }, b=2)` on a Function or `greeting({ a: 1 }, b=2)` on a Template, with `ValidationError` instead of merging the two objects; keywords after a positional source remain valid. On `.run()`, the keyword object is the argument object: `agent.run(context={ topic: 'recycling' }, temperature=0.2)`.

For Phase 3 LLMAgent, Cascada's marked keyword object is a trailing context argument even when history precedes it: `agent(messageHistory, topic="recycling")` normalizes to the rendered JavaScript call `agent({ topic: "recycling" }, messageHistory)`. This exception applies only to the marked keyword form; JavaScript `agent(messageHistory, context)` and Cascada's equivalent unmarked object-literal form are invalid for LLMAgent rendered calls. Recognize the marker before removing it and applying the ordinary argument order. Retiring factories retain their existing positional order.

Do not map plain positional values to schema fields. `lookupOrder({ orderId: 123, quantity: 2, accountId: 1 })` and `lookupOrder(orderId=123, quantity=2, accountId=1)` are equivalent direct component calls in Cascada. Fields are matched by name, optional fields can be omitted, and schema/property order has no invocation semantics. Keep each component's main-input/source/context forms, with rendered LLM history in the order defined above; named field inputs introduce no string-versus-source ambiguity. Source overrides can also use explicit fields in `.run()`.

## Phase 3: LLMAgent

Reuse Phase 2's closed tool-input contract for LLMAgent `.asTool`: declared top-level parameters, rejection of unknown raw keys before parsing, and nested dynamic data. Do not add an open-root escape switch or a second input schema. Native SDK tools remain unchanged.

Expose `LLMAgent` through a named export and `create`. Each returned component is callable and has `.run()` and `.config`. Non-tool forms implement the SDK's `Agent` interface. The ordinary call and `.run()` are the Casai calls and run in the component's mode. `.generate()` and `.stream()` exist only on non-tool forms for the SDK interface: they take the SDK's call arguments with a literal conversation, never prepare the configured prompt, and always generate or always stream. Document them only with SDK integration.

The original non-tool component remains usable with Agent/UI helpers, and authors can derive a matching tool from its configuration without mutating it. LLMAgent follows the call conventions shared by every model component:

- Ordinary calls take inputs only, by position, in the order main property, context, secondary input; settings go to `.run()`. The specialized components of Phase 5 follow the same rule.
- A call-time main property has the configured property's type, so `.run({ prompt })` on a `.withTemplate` LLMAgent is a template, just like the configured source. Literal SDK requests go through the SDK methods.
- Casai uses `messageHistory` for its conversation input and result. SDK method arguments and callback execution options retain native `messages`; triggering tool messages are not renamed or presented as the assembled result history.
- Results add `value` and top-level `messageHistory`; see [the result contract](#output-and-result-contract).
- One application `context` supplies data to prompt preparation and both hooks. SDK methods/UI helpers spell that same raw call input `options`; configuration and Casai `.run()` use only `context`, with one `inputSchema`.
- LLMAgent has no configured `messages`. Fixed guidance belongs in `instructions`, and examples or trimming applied to each request belong in a `prepareCall` hook. Phase 1's internal fixture also omits configured `messages`; only the old factories have that legacy setting until they are removed.

**Common data model:** one resolved configuration, one flat application context, one selected source/implementation, one application `inputSchema`, and one output contract. Parent/component/call inputs retain the established merge laws. LLMAgent uses `prompt` with its selected modifier and native `output`; Template uses `template` and implicit text output; Script/Function use `script`/`execute` and `schema`. Specialized components retain native result contracts.

### Loop Policy Is Separate from the Interface

Resolve configured and per-call settings, including Phase 3 inheritance, then pass an explicit `stopWhen` through unchanged. A one-step policy can execute tools; it does not automatically continue with another model call using their results. A step limit counts model steps, not individual tool calls. SDK `prepareStep` remains available in either policy.

Providing the `Agent` interface and selecting a stopping condition are independent decisions. Phase 1 checks the interface through internal fixtures; Phase 3 exposes it on LLMAgent. Template, Script, and Function do not implement this interface or acquire a model-driven loop; their native execution modes are independent of LLMAgent stopping conditions. No internal agent-mode flag or separate `loopCount` setting is introduced.

#### Casai Calls and SDK Calls

Phase 3 provides Casai calls and literal SDK calls because their input protocols differ. The ordinary call resolves its positional arguments by type into the same argument object as `.run()`; both run in the component's mode:

```text
Ordinary call / .run(arguments)
  -> normalize arguments; an undefined setting counts as not supplied
  -> resolve configuration and call context; prepare/validate application context once
  -> prepare the effective prompt once; normalize to messages and snapshot history plus the prepared turn
  -> run prepareCall(request, config, context); bind returned tools/context and wrap effective prepareStep
  -> install protected settings; generateText / streamText
  -> Casai result/history augmentation

SDK .generate(SDK arguments) / .stream(SDK arguments)
  -> map SDK options to raw call context; resolve configuration and prepare/validate context once
  -> combine configured SDK settings with the literal prompt/messages; normalize and snapshot messages
  -> run prepareCall(request, config, context); bind returned tools/context and wrap effective prepareStep
  -> install protected settings; generateText / streamText
  -> SDK result with top-level messageHistory added
```

The SDK path skips source loading and prompt rendering, but uses the same application `inputSchema`, selected defaults, private-binding protections and parsed context as Casai calls. A literal conversation never becomes template/script source or implicitly supplies context fields. #### Loop Finality and Buffering

An unrestricted tool loop cannot guarantee both final-step-only output and immediate token delivery: text emitted now may belong to a step that later calls a tool and continues. An append-only stream cannot retract it. Preserve output selection and buffer when needed:

1. Stream omitted/default text incrementally only when the answer-producing invocation is terminal under the provider's declared protocol and its final representation is stable. Explicit output specifications, including arrays and explicit text, use a promised final value. A custom array parser can reorder the final array even in a terminal step; do not forward native `elementStream` into `value`.
2. Otherwise retain candidate output until finality is established. Discard intermediate candidates from `value` when execution continues.
3. Release only final output, applying output availability and validation before successful completion. An unrestricted loop may emit nothing through `value` until it finishes; release buffered output without artificial typing delays.
4. Keep SDK `stream` live throughout. Selection must not rerun generation, synthesize activity events, or eagerly create unused branches.

Establish finality from execution control and the provider's declared protocol, never from prompt instructions, the absence of tool calls so far, or inspection of an arbitrary `stopWhen` predicate. When those controls permit continuation, buffer. Retry and transform handling must preserve the collection invariant: abandoned-attempt text cannot silently become final output. Follow the SDK's consumption, branching, buffering, and cancellation behavior rather than adding a separate Casai limit policy. Final-output selection still needs candidate buffering; avoid retaining additional copies of unrelated activity beyond the SDK views.

Use these finality conditions after `prepareCall` and the current `prepareStep` have resolved. They assume that the provider respects the tool protocol:

| Effective execution state | What is known | Release through `value` |
| :--- | :--- | :--- |
| Effective settings disallow tool calls, and no deferred provider-tool results can cause continuation | Under the provider protocol, this model step is terminal. Examples: no effective tools, `activeTools: []`, or effective `toolChoice: 'none'`, provided tool callers/provider mechanisms introduce no other continuation path | Incremental final-answer output is eligible, subject to stable retry/transform output, final validation, and rejection if the SDK unexpectedly continues |
| Tool calls remain possible, or effective tool/provider continuation state is uncertain | Eligible final output is not proven in advance, regardless of the stopping condition | Buffer until SDK execution establishes the final step, then release only eligible final output |

A tool without a local `execute` still matters: approvals, client-side tools, and deferred provider results can affect continuation and output availability. Do not equate “no executable tools” with “no tool calls possible.” Observe effective hook results without invoking hooks twice. Treat arbitrary stopping conditions as SDK-owned; do not inspect their bodies, call them against synthetic steps, or track whether the default was used. Even with proven terminality, buffer a default-text prefix if retries could replace it. Decide from the final request after `prepareCall`, not configured or pre-hook settings. In the installed SDK, `streamRetries: 0` permits a retry requested by `onError`; omitted `streamRetries` disables that retry path even when `onError` exists. Hook-added retry settings must not leak an abandoned prefix, and hook-removed settings must not force stale retry handling. Acceptance must include a call hook adding `streamRetries: 0` with retry-returning `onError`, positive automatic retries, removing either setting, and no retry with omitted `streamRetries`; abandoned-attempt text must never enter default-text `value`. The shared result adapter must receive the final request rather than pre-hook config. Custom output parsers always belong to the explicit-output promise path. A consumer may already have displayed that prefix before learning of the failure. Preserve native execution, result views, and history. This check protects the successful-collection invariant and does not impose a separate SDK continuation policy.

#### Stream Consumption

Follow the installed SDK's language-result ownership model for LLMAgent `value`. A default-text stream handle is consumable; accessing its getter again creates a fresh view of the same execution, without another model call or parse. Native SDK streams can replay through SDK buffering; final-result getters such as `output` and `steps` drive consumption automatically. Explicit-output `value` reuses a lazy final-value promise and does not iterate parsed output. If that output is a custom iterator, a later getter/await returns the same handle without restoring consumed elements. Add no Casai replay buffer. `value` retains final-output selection and terminal-error behavior; arbitrary component streams gain no replay guarantee.

Reuse SDK branching and buffering where applicable. The SDK retains a branch for later views, so the prohibition on unnecessary branches means no additional eager, unused Casai branches; it does not forbid the SDK's own replay mechanism. Breaking iteration over an SDK stream closes that consumer according to its native contract; it must not implicitly abort other SDK views of the execution. Request cancellation uses the invocation signal.

Function streams, and later native Script/Template streams, are directly returned stream handles rather than result objects with replay getters. Preserve ordinary consumption and cleanup. Passing a stream to a component permits consumption; returning that source does not restore unread status or consumed items. A lazy validation wrapper can change the returned object while retaining one producer and one pass, as described under [stream schemas](#stream-schemas-and-collection). StreamingTranscriber keeps the SDK's separate single-owner contract for potentially unbounded audio; it does not gain language-result replay.

#### Output Availability and Failures

Text selection operates on SDK model steps. The selected step's native parsed output retains all text that the SDK includes in that step, including commentary before provider-executed tools and OpenAI Responses message phases. Text blocks are concatenated without inserted separators; Casai preserves that SDK representation and the successful-collection invariant. It does not infer which prose is the answer.

**Accepted native OpenAI chat refusal limitation:** the installed chat adapter omits the response's `refusal` field from normalized content. A refusal may become `stop` with empty text, which is eligible for default text output just like an intentional empty answer. Structured output still applies its native parser and rejects invalid empty text. Preserve this contract; add no blanket empty-answer rejection or raw-body refusal reconstruction. This limitation is specific to the characterized adapter/API, not a claim about every OpenAI API.

Anthropic's raw `pause_turn` explicitly declares an unfinished server-tool turn. The installed adapter normalizes it to `stop`, so output eligibility checks the retained raw reason before accepting `stop`, including after server-tool results have arrived. Native SDK fields remain unchanged. Use the available history for an explicit continuation, following [Anthropic's stop-reason contract](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons).

Use one Casai output-availability rule in both modes and tool adaptation. Eligibility is a protocol decision about the completed execution, its final step, and unresolved tool work; it is not a guess about whether prose sounds like commentary or answers the user's question. Finality permits selecting a step; eligibility and the SDK's final parser determine whether its output can complete successfully. Select the SDK-reported final step without adding a fallback to an earlier step.

Apply the following rules in order. The table describes Casai views when an SDK result exists: a rejected `generateText` call still rejects, and Casai must not manufacture a result or history handle for it. `messageHistory` combines the invocation's dynamic conversation prefix with native `responseMessages`. It is available whenever those messages are available, even after an error finish reason or a provider failure, and propagates their rejection unchanged. It guarantees neither execution success, a complete exchange, nor safe resumability. This rule applies to every row below; Casai adds no history-specific failure gate.

**Accepted native structured-output limitation:** `generateText` eagerly parses `Output.object` and `Output.array` before returning a result. Invalid final structured text with `stop`, `length`, `content-filter`, or `other` can therefore reject with `NoObjectGeneratedError` even when tool calls are present. With `stop`, a local tool may already have executed before parsing fails. There is no result handle or Casai `messageHistory` to return, although native callbacks may already have received response messages. Preserve this SDK outcome and do not retry automatically. Prefer streaming when resumable structured executions require a returned history handle: streaming retains history after completion while `value` rejects with `NoOutputGeneratedError` for pending work or the native parser error for otherwise eligible output. Characterize these differences against the native SDK on upgrades.

**Accepted native generation-cancellation limitation:** `generateText` and `ToolLoopAgent.generate` can return normally when an invocation signal aborts while a tool is running and a stopping condition ends the loop before another model step. A cooperative tool's abort becomes a tool error; a non-cooperative tool may finish with its result. Casai preserves that returned result and applies ordinary final-step output eligibility: a `tool-calls` ending has no final `value`, while native history remains available. Add no Casai abort listener or cancellation tracker to reinterpret a normally returned result. Native streaming completion rejects with the abort reason in the characterized cases. Recheck both modes, cooperative/non-cooperative tools, and Agent behavior on SDK upgrades.

**Accepted native SDK exception:** in `ai@7.0.130`, a continuation's `prepareStep` or provider call can throw before returning a stream. The SDK reports the error through `onError`/events but can resolve its result promises with earlier completed steps. Casai preserves that outcome: history remains available, and `value` follows the eligibility of the SDK-reported final step. An earlier `tool-calls` step still has no eligible value; an earlier `stop` step with resolved tools can supply its parsed output. If no step completed, native result promises may reject with `NoOutputGeneratedError` rather than the setup error; `value` reuses an already-captured attempt error for a cause-less native rejection, as described above. Add no Casai failure tracker or extra success gate for already-resolved native completion. Recheck the characterization tests when upgrading the SDK. Failures inside a returned continuation stream and rejected SDK completion promises remain covered by the table.

| Completed execution or final-step state | Casai `value` in either mode |
| :--- | :--- |
| SDK completion rejects, reports an abort/timeout, or final `finishReason: 'error'`, including after an earlier successful step | Fail with the reported completion/abort reason. If the SDK reports only an error finish reason without a cause in that attempt, use `NoOutputGeneratedError`; never return recorded text as success |
| Final raw finish reason is Anthropic's `pause_turn`, including when normalized to `stop` and all server-tool results have arrived | No eligible output: pause-specific `NoOutputGeneratedError`. Retain native history for explicit continuation |
| Execution paused with an unresolved approval, client tool result, or supported deferred provider result, even when text is present or the finish reason is `stop` | No eligible output: `NoOutputGeneratedError` |
| Final finish reason is `tool-calls`, including when local tools have executed or been denied and a stopping condition prevents another step | No eligible output: `NoOutputGeneratedError`; accompanying text is not a final answer |
| Final finish reason is `stop`, with no unresolved tool work | Reuse final SDK parsed `output`. Empty text is valid if that parser accepts it |
| Final finish reason is `length`, `content-filter`, or `other`, with nonempty final-step text and no unresolved tool work | Reuse final SDK parsed `output` if it succeeds. Preserve the finish reason; this does not promise an untruncated or semantically complete answer |
| Final finish reason is `length`, `content-filter`, or `other`, with empty final-step text | No eligible output: `NoOutputGeneratedError`, matching generation's availability rule even if streaming's raw `output` resolves |
| An otherwise eligible final step fails SDK output parsing or validation | Propagate that native output error; never report successful collection or return an earlier parsed output |

A completed provider-executed tool and answer in the same final step do not disqualify the answer. Nor does a resolved local tool call by itself: use the finish reason and unresolved-work rules, not `toolCalls.length > 0`. An earlier step's tool use likewise does not disqualify a later answer. Match calls, approvals/denials, final results, and tool errors through SDK identifiers and content/history; preliminary results do not resolve a call. Retain approval-ID matching: streaming provider denials need not produce a synthetic `execution-denied` tool result, so a denial response itself must clear that pending call. Local denials ordinarily have the SDK's synthesized result. Only provider mechanisms with a declared deferred-result contract imply deferred work from an absent result. Do not invent a provider continuation protocol or infer pending work from every provider tool event.

Pending work also survives invocation boundaries. The SDK already rejects incoming history with unresolved local/client tool calls or unanswered local approvals before dispatch: generation throws `MissingToolResultsError`; streaming reports it through `onError` and its completion can reject with `NoOutputGeneratedError`. Preserve those native checks. Casai's cross-turn scan additionally covers provider-executed calls with pending deferred results or provider approvals that the SDK permits in incoming history. For LLMAgent, snapshot one original conversation before `prepareCall`: assembled history plus the prepared new turn on Casai calls, or the literal conversation on SDK calls. Use it both as the `messageHistory` prefix and as the incoming portion of the pending-work scan, followed by native `responseMessages`, which includes pre-step approval results and excludes preliminary results. Do not reconstruct this source from the post-hook sent request. Trimming in either `prepareCall` or `prepareStep` does not resolve pending conversation work, and a later answer remains ineligible while that work is unresolved or undenied. The retiring factories' separate static-message input source is needed only until their removal; it is not a second LLMAgent conversation model. See [the reproduced handoff gap](phase3-review.md#conversation-before-request-hooks).

Unavailable complete `value` access throws; a stream-valued `value` rejects during iteration, and a promised `value` rejects. A successful streamed value must pass the same terminal and final-parse checks before closing successfully. Delivered prefixes remain delivered if a later check fails. Recovered provider attempts and recoverable `tool-error` events do not automatically fail the execution; resolved tool errors can be followed by an eligible answer. Preserve native SDK errors, result fields, event delivery, and validation without revalidating transformed output. Keep history tied to the native messages rather than the `value` completion gate. A later abort cannot retroactively invalidate settled native results.

Casai's `NoOutputGeneratedError` messages explain tool-call termination, provider pauses, pending tool results/approvals, empty non-stop output, or an error ending without a reported cause. These messages are diagnostics, not a machine-readable status contract. A UI uses native finish reasons, including raw provider reasons, and tool/approval events to identify pending work; it must not parse error wording or treat resolved `messageHistory` as proof of a pause. History can also remain available after execution failure, empty truncated output, or final output parsing failure; its resolution is not an outcome discriminator. Save an ordinary answer only after successful `value` completion, inspecting the finish reason when truncation matters. Save legitimate pending tool/approval history deliberately based on protocol events. Keep prior history after failure unless retaining partial work is an application decision; observe native error events for the accepted SDK exceptions too.

## Cancellation, Timeouts, and Usage

Before Phase 7, delegate native cancellation to the SDK: forward the per-call `abortSignal` and the final hook-selected `timeout` unchanged. Resolve timeout from configuration/call settings before `prepareCall`; its complete editable return can replace or omit that timeout. The SDK owns timeout timers and provider/tool cleanup. Its total timeout starts at SDK execution; it does not include preceding Casai parsing, loaders, or rendering. Signals belong to invocations: reject constructor `abortSignal`, including inherited configuration, and retain it on `.run()` and SDK methods. LLMAgent tool adapters in both execution modes explicitly forward their SDK tool-call signal through the shared prepared-execution path. Add no configured-signal merging or automatic propagation through arbitrary nested calls.

Before Phase 7, Function callbacks and `.withFunction` preparers receive explicitly supplied signals through execution options. Phase 3 request/step hooks read that same explicit invocation signal through `context._toolOptions.abortSignal`, including on SDK entry paths. Native step information has no abort-signal field. This exposes the caller's signal, not the SDK's later internal timeout signal; no caller signal means that metadata field is absent. Script/Template `.run()` also accepts a signal for pre-start checks and explicit forwarding to injected registered tools; an SDK tool entry captures its native signal for those wrappers. Await callbacks and Cascada rendering normally, then check the caller signal before starting the SDK backend. Arbitrary functions/components supplied in context receive no automatic propagation. Add no timeout race without async call context to carry the deadline into nested calls. Script/Template timeout settings and Function timeouts are not Phase 2/3 features; native engine abort support is separate.

Shared invocation deadlines and automatic nested propagation belong to [Phase 7](#phase-7-async-call-context-and-deadlines). Cascada async call context carries an absolute end time and call ancestry; a child uses the earlier of its inherited end time and its own timeout from entry. Signals are boundary controls for SDK/cooperative operations, not mandatory invocation state. With context in place, timeout races are acceptable for Function, Script, and Template before native engine abort exists. The Phase 1 implementation contains no shared timer or parent/child invocation scope, and Phase 2 has no dependency on one. See [abort.md](abort.md) for the deadline and lifecycle contract.

Verify native SDK timeout/signal forwarding, original abort reasons, terminal failure in `value`, native message availability/rejection in history, and unchanged configuration. Cooperative JavaScript checks verify explicit forwarding and no later backend dispatch after awaited preparation reports cancellation. Phase 7 verifies inherited end times, async call ancestry, race limits, late-running work, and stream lifetimes. Actual engine interruption tests follow the native capability.

LLMAgent reports its own SDK usage and callbacks. Phase 7 uses the Cascada async call context developed with telemetry to identify parents and nested calls, including calls through ordinary JavaScript. Whole-workflow usage reporting is a separate consumer of that foundation; Casai adds no parallel call tracker. See [future.md](future.md).

## Phase 4: Tool Continuations

Build on Phase 3's basic conversation history to add `resume({ messageHistory, approvals, toolResults, ...settings })` and the `approvals` and `toolResults` fields of `.run()`. This is Casai convenience over the SDK message protocol, not a method supplied by the SDK Agent interface. It normalizes continuation input, then runs an ordinary execution. Nothing else depends on this phase; it does not gate the initial LLMAgent release, specialized components, or native streaming.

Before implementing `resume()`, follow the [native continuation references](#native-sdk-reference) from `ToolLoopAgent` into core generation/streaming, approval validation, and message handling. Compare model-message and UI continuations with native behavior. Delegate execution and historical approval validation to the SDK; add only the input normalization and convenience checks described below.

An approval may resume in a later request with a newly created component/binding. Apply [approval configuration stability](#sdk-tool-boundary-and-configured-defaults): reconstruct the public defaults used by the approved raw arguments so their parsed public input stays identical. Request-derived locale, account, or other declared defaults must not silently change an approved operation. Private dependencies can change between bindings. A changed default hidden by an explicit approved argument does not change effective input and remains valid. Application persistence owns any required public configuration; Casai adds no snapshot store or history rewriting. When revalidation differs, retain the native tool error and non-execution rather than promising `resume()` succeeds.

For UI-helper continuation, expose those public defaults through `agent.tools` before helper entry; its historical validation precedes `prepareCall` and may reject the request without invoking the agent. Do not conflate that failure with the model-message continuation's tool-error result. Both use native SDK behavior.

### Continuation Inputs

`approvals` and `toolResults` continue a conversation whose last turn ended in tool approval requests or tool calls without results. They require `messageHistory`, exclude `prompt`, and append one `tool` message with SDK `tool-approval-response` and `tool-result` parts; nothing is rendered and no user turn is added. Match each decision and result against the calls still pending in `messageHistory`, and reject unknown, duplicate, or already-resolved IDs and pending non-automatic requests left without a decision. Each result entry has exactly one of the own properties `output` or `error`. `output` is the completed application result that the tool's `execute` would return, not an already-encoded SDK result part; a present `output: undefined` is still a success value. Convert successes through the registered tool's `toModelOutput` with the matched call ID and input. Without that converter, including for an unregistered external tool, use the SDK default: text for strings and JSON-normalized output for other values. Convert `error` through the SDK error-text path, bypassing the success converter. Reject contradictory decisions/results, including a success supplied for a denied call, before executing anything. An approved call with an external result must not execute again. Persistence and deduplication across requests belong to the application.

`resume({ messageHistory, approvals, toolResults, ...settings })` is the public continuation method. It runs in the component's mode, generating or streaming on `.asStream`; `.run()` accepts the same fields. Its result carries `messageHistory` like any other call, so applications can persist it between requests. SDK UI helpers don't use it: the UI client sends approval responses within the complete conversation.

### Phase 5 Modifier Contracts

Support every existing modifier with meaningful semantics for the component. The [README2 support matrix](../README2.md#modifier-support) specifies the planned combinations; it is a requirement for Phase 5, not an inventory of undecided features.

- `Decision`, `Embedder`, `Reranker`, `ImageGenerator`, and `SpeechGenerator` support `.withText`, `.withTemplate`, `.withScript`, `.withFunction`, `.loadsText`, `.loadsTemplate`, `.loadsScript`, and `.asTool`.
- `Transcriber` supports `.withScript`, `.withFunction`, `.loadsScript`, and `.asTool`. `StreamingTranscriber` supports those preparation modifiers, but `.asTool` is available only after `.withScript`, `.withFunction`, or `.loadsScript`. The preparer turns named tool arguments into a bounded raw-audio stream; the tool collects the completed transcript. The plain factory exposes no `.asTool` in either types or runtime modifier properties.
- `VoiceSessionSetup` supports all seven text/script/function/loading modifiers for preparing session instructions. It has no `.asTool`.
- No phase exposes a public `.asAgent` modifier. `.asStream` belongs to `LLMAgent` until Phase 6 extends it to Template; Script, Function, and specialized components do not use it. Phase 6's coded components keep native contracts. None of these features adds Agent assignability or a tool loop to a specialized operation.

Modifiers apply only where their output fits the operation's input. Text/template preparation targets decision text state, a single embedding value, the reranking query, image prompt text, speech text, or voice-session instructions. A text or template modifier produces one string, so it never prepares an embedding batch; Script and Function preparers can return a string array for `embedMany`.

Each component's main property is the field named after the input it prepares: `state` (Decision), `value` (Embedder), `query` (Reranker), `prompt` (ImageGenerator), `audio` (Transcriber, StreamingTranscriber), `text` (SpeechGenerator), and `instructions` (VoiceSessionSetup). As on LLMAgent, a call-time value in that field has the configured value's type and replaces it for one call. Keep separately configured documents, image references, and masks intact when preparing text. `.loadsText` and `.loadsTemplate` use the normal text loader contract.

Script and function preparation can return the component's typed input: native decision state; a string or string array for embeddings; a query string or explicit `{ query, documents }` for reranking; an SDK image prompt; recorded audio values; a live audio stream; speech text; or session instructions. Only these declared input fields can come from a renderer; arbitrary configuration and fixed result contracts cannot be replaced through its output. For an explicit reranking input object, its query and documents form one prepared input and must not be mixed with another input's documents.

Parameterize preparation validation by the operation's input type. The existing language prompt validator (`string | ModelMessage[]`) cannot validate audio streams, embedding batches, or image-editing input. Preserve non-JSON values, binary data, and streams without cloning, stringifying, or consuming them. `.withScript` and `.loadsScript` return values directly; a `.withFunction` preparer receives the prepared context, including `_toolOptions` under the Phase 2 execution-metadata contract. Generalizing preparation must not weaken existing language-message validation.

Rendered variants take rendering context in the ordinary call and `.run({ context, ...settings })`. Resolve configured/call input and private/trusted sources, then apply each input schema once before preparation consumes the parsed context plus bindings. Ordinary calls take no settings, so argument keys never classify context versus settings. Renderer type and result-defining contracts stay fixed at creation; per-call main properties follow the selected renderer's convention. Runtime state remains invocation-local.

Transcribers have no text/template modifiers for their audio payload. Even a base64 string is audio data rather than prompt text, and a text loader does not open a raw-audio stream. Script/function preparation can fetch audio or create a stream, while `inputAudioFormat` and other settings use the ordinary configuration path. Do not consume live input while preparing the call. Voice instructions are prepared once for each new session, never for every incoming audio chunk, and the session owns connection cleanup and cancellation.

Completed-result components support `.asTool` after any of their applicable input modifiers. Reuse description/input-schema requirements, validation, execution context, and callable-tool composition. Without an input modifier, tool arguments are the operation input; with one, they are the preparation context. The `execute` result goes to the application and UI, and the SDK tool option `toModelOutput` decides what the model receives:

| Component | Tool arguments without a modifier | `toModelOutput` default | `execute` result |
| :--- | :--- | :--- | :--- |
| Decision | `{ state }` | Answers | Answers |
| Embedder | `{ value }` or `{ values }` | Vectors | Vectors |
| Reranker | `{ query }` only; candidates from configured `documents` or a preparer | Top `topN` `{ document, score }` entries | The same entries |
| ImageGenerator | `{ prompt }` | Content output with image file parts | `{ mediaType, base64 }` per image |
| Transcriber | `{ audio }`, as a URL | Transcript text | Transcript text, segments, and metadata |
| StreamingTranscriber | No plain tool form; requires a preparer whose context is defined by `inputSchema` | Final transcript text | Final transcript text, segments, and metadata |
| SpeechGenerator | `{ text }` | A short text confirmation | `{ mediaType, base64 }` |

`.asTool` accepts a user `toModelOutput`, for example to send text instead of images to models that can't read images in tool results; the SDK exposes no image-input capability flag for an automatic check. Image content in tool results is converted by the installed Anthropic provider and OpenAI's Responses API, so no prompt rewriting is needed. Keep `execute` results serializable for UI tool parts. Preserve full results for direct invocation; a universal `.output` accessor or binary-to-string conversion is insufficient. A StreamingTranscriber tool takes serializable named preparation arguments validated by `inputSchema`, such as `{ recordingId }`, never a model-supplied stream. Its script/function preparer opens a fresh raw-audio stream for each execution, with finite input or an explicit normal completion boundary and the configured audio format. Do not share a consumable audio source across tool calls. Collect the final transcript once, not concatenated partial/final events; direct component calls retain the live SDK result. Do not drain an indefinitely open voice session to manufacture a tool result.

### Ordinary Calls

Each specialized component's ordinary call follows the common rule: inputs by position, settings only through `.run()`.

- Plain form, without an input modifier: `component(input)`, where `input` is the operation's main input. Reranker takes `(query, documents?)`. The main input can itself be an object or an array, such as an Embedder batch or an image-editing prompt, so plain forms resolve arguments by position, not type.
- With a text, template, or script modifier: `component(context)` or `component(main, context)`, where `main` is a one-off template, script, or resource name, as on Template and Script. With `.withFunction`: `component(context)`.
- The order is always main property, context, secondary input, so a rendered Reranker takes `reranker(context, documents)`.
- From Cascada, keyword arguments arrive as a final object. A rendered component's `route(customer=name)` passes context. A plain component takes them through `.run()`: `speaker.run(text='Hello', voice='alloy')`.

| Component | Plain ordinary call | `.run()` | Example |
| :--- | :--- | :--- | :--- |
| Decision | `(state)` | `{ state, ...settings }` | `route('My order arrived damaged.')` |
| Embedder | `(valueOrValues)` | `{ value }` or `{ values }`, with settings | `embedder(['First', 'Second'])` |
| ImageGenerator | `(prompt)` | `{ prompt, ...settings }` | `illustrator('A watercolor workshop')` |
| Transcriber | `(audio)` | `{ audio, ...settings }` | `transcriber(recordedAudio)` |
| StreamingTranscriber | `(audio)`; `inputAudioFormat` is usually configured | `{ audio, ...settings }` | `transcriberStream(audioStream)` |
| SpeechGenerator | `(text)` | `{ text, ...settings }` | `speaker('Your replacement is on its way.')` |
| Reranker | `(query, documents?)` | `{ query, documents?, topN?, ...settings }` | `reranker(question, candidates)` |
| VoiceSessionSetup | `(instructions?)`; rendered forms take context | `{ instructions?, context?, ...settings }` | `support({ company: 'Acme' })` |

Reranker candidates usually change on every call, so they come second; with configured documents, `reranker(question)` is enough. VoiceSessionSetup's ordinary call prepares a browser session; `executeTool()` stays a named method.

### Embedder Calls and Results

Accept a string or an array of strings directly. No `value` wrapper is required on the callable. The array always means a batch; never concatenate it into one input or reinterpret it as message parts.

```typescript
// Proposed Phase 5 API. embeddingModel is supplied by the application.
const embedder = create.Embedder({ model: embeddingModel });

const one = await embedder('First document');
console.log(one.embedding); // number[]

const many = await embedder(['First document', 'Second document']);
console.log(many.embeddings); // number[][], in input order

// Per-call settings go through .run(), with the SDK input field names.
await embedder.run({ values: ['First document', 'Second document'], maxParallelCalls: 2 });
await embedder.run({ value: 'Another document', abortSignal: AbortSignal.timeout(5_000) });
```

Implement string and array overloads with their corresponding SDK result types. On the plain component, `.run()` accepts exactly one of `value` or `values`. Settings apply to that invocation only; neither form mutates `.config`. Rendered variants follow the [modifier contracts](#phase-5-modifier-contracts): text and template preparation yields one value, while script/function preparation yields one value or a batch. Do not change the existing LLMAgent context argument convention.

Delegate to `embed` / `embedMany`, preserving SDK settings, usage, warnings, metadata, and responses. Let the SDK handle batch splitting and concurrency; do not implement batches as unrelated calls to `embed`. Keep batch-only settings such as `maxParallelCalls` on the array path. A future multimodal input form must be explicit and preserve the meaning of `string[]`. See [SDK embeddings](https://ai-sdk.dev/docs/ai-sdk-core/embeddings).

### Reranking and Decisions

Reranking commonly improves RAG after initial retrieval: retrieve candidates using vector, keyword, or hybrid search, rerank them against the query, then provide the best candidates to the answering agent. It also serves ordinary search and recommendation workflows. `Reranker` uses the SDK's `query`, `documents`, and `topN` semantics and preserves original indices, relevance scores, and document values. It does not create embeddings or manage a vector database. See [SDK reranking](https://ai-sdk.dev/docs/ai-sdk-core/reranking).

`Decision` preserves the SDK's named questions, answers, optional distributions, provider metadata, and refusal/error behavior. It can be composed before an agent for routing or exposed through a tool adapter. Choosing an enum or `Output.choice()` on an LLMAgent continues to use language generation; it does not select the Decisions endpoint. The installed SDK exposes `experimental_decide`; provider capabilities and experimental contracts must be checked against the version used for implementation. See [SDK decisions](https://ai-sdk.dev/docs/ai-sdk-core/decisions).

### Transcription and Voice

Streaming transcription is supported by the installed `ai@7.0.130` as `experimental_streamTranscribe`. `StreamingTranscriber` requires a model that supports streaming, raw audio chunks, and the matching `inputAudioFormat`. Preserve transcript delta/partial/final events and final transcript metadata. Return the live SDK result without waiting for completion; asynchronous Casai preparation may require a promise for that handle. Unsupported models must report an error rather than silently buffer a complete recording.

The SDK result's `fullStream` has a single consumer. Access it before final-result promises when both events and the final transcript are needed; awaiting a final result first consumes the stream internally. Casai must not consume it during preparation or result augmentation. See [SDK streaming transcription](https://ai-sdk.dev/docs/ai-sdk-core/transcription#streaming-transcription).

Keep this native transcription contract rather than adding `textStream` or `partialOutputStream` aliases, and add no Casai `value`: when transcription is stopped or fails, its stream ends as the SDK ends it. How live transcription ends is less deterministic than the other components, whether it is stopped or fails, and the transcript received up to that point is still needed, so it is kept rather than discarded by a whole-stream failure. Incremental consumers handle transcript events explicitly; a workflow can await `text` for the final transcript. Phase 6 does not automatically forward transcription events into a Template or Script text stream. A future adapter would need explicit event and consumption semantics.

`Transcriber` handles complete recordings and returns the SDK transcript result. `SpeechGenerator` preserves generated audio, media information, and provider metadata. Neither operation is a persistent conversation. See [SDK speech generation](https://ai-sdk.dev/docs/ai-sdk-core/speech).

`VoiceSessionSetup` is the server half of the SDK's browser realtime design. In the installed SDK, the browser session (`AbstractRealtimeSession`) owns connection, audio capture and playback, text input, interruption (`cancelResponse`), and tool-call delivery (`onToolCall`, `addToolOutput`). The server creates a short-lived client secret through the provider, with `sessionConfig` carrying instructions and voice, and returns a `RealtimeSetupResponse` of `{ token, url, expiresAt, tools }`.

- The ordinary call, or `.run({ context, ...settings })`, validates input, prepares `instructions` once, builds tool definitions with `getRealtimeToolDefinitions`, creates the client secret, and returns the setup response. Each call starts an independent session; the component stores no session state.
- `executeTool({ toolCallId, toolName, args }, { toolsContext, abortSignal })` receives the browser call separately from trusted server settings. Resolve the tool in the server-owned configuration used for that session, parse arguments and selected trusted context separately, and execute once with cancellation. Reject unknown or unavailable tools. Bind both HTTP routes to the same server-owned tool configuration; retain/recover session-specific configuration in the application, not mutable component state or browser arguments. Casai callbacks receive the validated fields in their flat context under the common tool-execution contract.

Casai handles no audio or browser transport. A separate live `VoiceSession` contract remains planned: realtime models declare a `server-websocket` connection (OpenAI's Live API requires it), and the SDK exports audio encoding and resampling helpers. A server session would accept a raw audio input stream with its format, matching StreamingTranscriber, and return session events with output audio, transcripts, and interruptions. Casai would own the provider connection and the session loop that the browser class implements today; applications bridge their own transport. It is not a `StreamTextResult` or an implementation of the SDK Agent interface. See [SDK realtime](https://ai-sdk.dev/docs/ai-sdk-core/realtime).

## Phase 6: Cascada Streaming Integration

Integrate Phase 2's JavaScript stream contracts and Phase 3's LLMAgent streams with new Cascada capabilities. Template gains streaming rendering, and Script gains native stream channels with live return. Function producers, Script JavaScript-iterable returns, stream schemas, collectors, and finite root-stream tool collection already belong to Phase 2; LLMAgent `value` and streaming-agent tool collection belong to Phase 3. Do not postpone those features to this phase. Coded components retain native values and streams and do not manufacture SDK results or events.

### Execution Modes

Only components whose engine can run in two ways have `.asStream`:

| Component | Complete | Streaming | `.asStream` |
| :--- | :--- | :--- | :--- |
| LLMAgent | SDK `generateText` | SDK `streamText` | Yes |
| Template | Cascada `renderString` | Future Cascada `renderStringStream` | Yes |
| Script | Runs once and returns its value | Returns a live `stream` or `tstream` channel with a matching schema | No |
| Function | Calls `execute` once and returns its value | `execute` returns an async iterable when its schema declares a stream | No |

Script and Function have no `.asStream`: their schema declares their return. LLMAgent and Template inherit streaming mode from a parent; deriving through the base factory does not turn it off. No reverse-mode modifier is added. Calling an independent child inside a workflow instead preserves that child's own mode. Each invocation executes once, including when a tool adapter collects it.

LLMAgent delegates the requested SDK mode directly. A provider offering both methods does not guarantee native incremental output for every model; SDK streaming simulation may be configured explicitly, and Casai does not add that fallback silently. See [SDK middleware](https://ai-sdk.dev/docs/ai-sdk-core/middleware#simulate-streaming).

### Cascada Capabilities

- **Implemented in the installed engine:** loops consume JavaScript async iterables from context, including async generators, with automatic sharing by default. The public `makeSharedIterable` helper provides explicit JavaScript replay; values passed to JavaScript or returned from a script otherwise retain native consumption. This is existing [runtime behavior](#stream-ownership-and-runtime-responsibilities), not a new Phase 2 dependency. Calls into JavaScript functions pass keyword arguments as one trailing object marked `__hasKeywordArgs` (`runtime.makeKeywordArgs`).
- **Future:** distinct `stream` and `tstream` channels with live return, plus `renderStringStream` returning `tstream`. A script declares `stream s` or `tstream s`, emits through `s(value)`, and returns it live with `return s`. Channels follow source order. Assigning a channel takes a snapshot of its emitted prefix, an array for `stream` and a string for `tstream`; a JavaScript stream assignment instead retains its reference. Native stream error termination, healthy complete returns, schema validation, and cleanup belong to Cascada, not a Casai consumer-dependent adapter.

Template rendering and native Script channel returns depend on these upstream capabilities. Existing loops already consume Phase 2 JavaScript streams. Casai matches text/element schema kinds to native `tstream`/`stream`, requires Script return kinds to match their schemas, and uses Cascada's ordinary rendering and return APIs. Cascada owns snapshots, validation, error handling, and native stream termination. Confirm the actual upstream APIs when implementing Phase 6; no separate internal-call/export boundary protocol is a Casai prerequisite.

### Composition and Template Rendering

The parent's mode does not switch a child's ordinary call. A child streams when it was created with `.asStream`, or is a Script or Function whose schema declares a stream. A Template forwards a child text stream while streaming and collects it during complete rendering, from the same source. A child LLMAgent's `value` contains only final application output in either parent mode; unknown loop finality may delay delivery without changing the resulting text.

Assignments, filters, property access, function arguments, and Script intermediate calls preserve the child's declared contract. A regular LLMAgent's `value` is its complete output. In either parent mode, a streaming LLMAgent's `value` is a final-text stream when `output` is omitted, or a promise of the completed parsed value for any explicit SDK `Output`. Awaiting that promise or a final SDK result property intentionally waits for completion.

Do not detect LLMAgent results at text-rendering boundaries. A template reads `.value` explicitly, as a Script does, and renders the string or forwards the native stream it gets. Transcription events are not text; a template adapts them explicitly. Preserve the producer, declared kind, and consumption state across JavaScript/Cascada boundaries. Necessary schema or result adapters may return a different stream object without duplicating its producer.

Cascada delivers selected output in logical source order while independent producers run concurrently. It releases each available prefix and buffers later positions at gaps; Casai forwards that output without collecting the entire workflow to simulate streaming. Intermediate values stay internal until selected for output.

### Lifecycle

Awaiting a streaming call returns its live handle without draining it. Extend the existing [consumption contract](#stream-consumption) by using Cascada's native `stream`/`tstream` behavior directly:

- **Complete returns:** Cascada returns a complete healthy value or its poison/failure outcome. Casai does not accept partially failed objects and inspect or repair them itself.
- **Stream returns:** Cascada delivers healthy text/elements in source order and terminates at the first error. Preserve any delivered prefix; do not yield the failed item or later items. This behavior belongs to the native stream type, not to a Casai distinction between Script and JavaScript consumers.
- **Schema parsing:** pass declared schemas through the engine's supported API and use its parsed healthy values/elements. Do not reparse SDK/Cascada results, scan poison, or invent internal-call hooks. If the upstream API only validates without returning parsed values, align that API before Phase 6 rather than add a Casai transformation pass. JavaScript Function producers use Phase 2's lazy parser because Cascada does not produce those values.
- **Ownership and cleanup:** preserve the engine's backpressure, signal, closure, and ownership contracts. Returned streams remain live after the call resolves. Casai forwards supported cancellation and closure; the runtime owns shared-source cleanup, and interrupting an in-flight await still needs cooperation.
- **Collection:** collectors and tool adapters consume the returned stream once and propagate failure; they never report a successful partial string/array after an error. SDK events and transcription retain their SDK protocols.

Local recovery before producing a returned value remains Cascada language behavior. Casai does not add a promise that a parent can resume an already-failed returned stream, provide parallel strict/recoverable views, or infer the consumer from context or call stacks. No separate boundary-protocol feasibility project is required by this plan.

## Phase 7: Async Call Context and Deadlines

Deferred until Cascada provides async call context, developed together with its telemetry foundation. This phase builds on Phase 2 invocation conventions, Phase 3 for LLMAgent integration, and that context API. It does not require Phase 6 streaming, a completed telemetry reporting API, or native Script/Template abort support. Out-of-order streaming is separate Phase 8 work.

The inherited control is an absolute end time. At invocation entry, resolve `endTime = min(parent.endTime, invocationStart + effectiveTotalTimeout)`, treating an absent bound as unlimited. The local total timeout follows the existing configuration/call override rules. This one budget covers asynchronous schema work, loaders, rendering, hooks, backend execution, and returned live streams. Children may shorten the parent budget, never extend it; neither dispatch nor returning a stream restarts the clock.

LLMAgent's confirmed broader `prepareCall` can select a final timeout after preparation. Apply that total from the original invocation start, bounded by the inherited parent deadline; never restart elapsed time or revive an expired call. The initial deadline governs preparation until the hook returns, and a newly selected total already consumed rejects before dispatch. The user confirmed that an active local deadline may be shortened, lengthened or removed: recompute it from the original start and final timeout, still capped by the parent. A 30-second call changed to 60 seconds after 5 seconds has 55 seconds left. Omission removes only the local total bound. Existing child calls retain their entry-time deadlines; subsequent children inherit the new deadline. Clear the completed preparation wait's timer and enforce the selected deadline for remaining execution without changing call identity, mutating prior contexts or tracking descendants. See [the deadline design](abort.md#phase-7-async-call-context-and-deadlines). This adds no Phase 3 timer machinery. Native step hooks do not gain timeout overrides.

Cascada's async call context carries the end time, call identity, and parent relationship through Script/Template calls, SDK tools, and ordinary asynchronous JavaScript. This supplies the call tree/ancestor stack needed by telemetry without explicit argument threading or a Casai call tracker. Function implementations can query the current context. Keep application/schema context separate, child contexts isolated, and late-running work and stream execution attached to their original context.

Keep the invocation path simple: read the parent context, compute the end time, enter the child context, check expiry, and execute. Add Script/Template and Function timeout settings here. With async context available, race their asynchronous completion against the remaining time, including preparation where needed. Reject expired calls before execution and recheck before backend dispatch. Clear race timers on settlement and handle late rejection. The race ends the caller's wait; arbitrary JavaScript and pre-abort Cascada rendering may continue, but their nested component calls remain bound by the inherited deadline. Synchronous code cannot be preempted by a timer.

Create deadline signals only at SDK or other cooperative boundaries that need them, combining an explicit caller signal there when needed. A signal is not the inherited budget, and an invocation need not own an abort controller. Omit only the SDK total timeout already enforced by a boundary deadline signal; preserve SDK step/chunk/tool limits and native cancellation behavior. Keep deadline enforcement alive through the underlying stream execution, without cancelling unrelated readers. Share small concrete helpers where useful; do not restore the generic signal-dependent `createInvocation` lifecycle.

Verify the deadline calculation, hook-selected totals and omission, shortening/extension and preparation-timer cleanup, elapsed-time accounting, expired initial/selected deadlines, parent caps, captured versus updated child deadlines before/after the hook, nested and concurrent calls, context queries from JavaScript, preparation/execution sharing one budget, timeout races, late-running work attempting new child calls, SDK signal adaptation and failure reasons, and returned-stream lifetime/cleanup. Native engine abort can later stop rendering and clean up owned work using the same end time; that stronger guarantee gets its own integration tests when available. The full contract is in [abort.md](abort.md).

## Phase 8: Out-of-Order Streaming

Deferred until ordered native streaming is established and an application needs positioned delivery. Keep the direction from [Cascada's streaming proposal](https://github.com/geleto/cascada/blob/master/docs/cascada/streaming.md#javascript-stream-integration), without committing public property names or payloads now. The stream schemas belong to Phase 2, and native Script channels and their runtime bridge belong to Phase 6; positioned views and `at()` remain separate proposed capabilities, not installed exports.

### Ordered and Unordered Output Properties

An ordered stream waits at a gap; a positioned view could expose a ready chunk before preceding positions finish. Both must assemble the same final text or array. Limit the proposal to text chunks and complete array elements. Preserve SDK events/UI transport and LLMAgent's existing partial-output getters; do not add unordered partial objects.

Use immediate hierarchical positions when possible, spelling a future JavaScript field `indexPath`. A flat index may depend on unfinished nested regions; do not promise both coordinates or a `Promise<number>` payload until the upstream protocol supports a reliable combined record and an application actually needs it. Network transport requires a concrete serializable position protocol.

### Integration Constraints to Retain

- Position-aware loop integration should preserve ordinary Script/Template loop bodies and raw item values. JavaScript may consume an explicit positioned record. Recognize a source protocol, not incidental application fields named `chunk`, `index`, or `indexPath`.
- Ordered and positioned views must refer to the same producer/emission; repeated identical chunks are distinct. A wrapper around already-ordered output cannot recover earlier availability.
- Preserve source-order visibility, guard rollback, and cancellation. Provisional output cannot leak through a positioned view. Final text/arrays remain logically ordered.
- Define one-consumer/branch behavior, backpressure, bounded buffering, early exit, failure, and unresolved positions before advertising additional result properties. Do not create hidden eager tee branches.
- Define duplicate/missing position errors and cleanup rather than allowing completion to hang. Compare paths numerically, not as strings or JavaScript arrays.

Revisit the proposed paired stream properties and positioned producer helpers after those prerequisites. The core remains useful with ordinary ordered async iterables, and independent workflow operations remain concurrent.
