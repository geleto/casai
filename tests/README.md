`npm test` runs the mock runtime suite. Register new mock-only files in `.mocharc.json`. Use `test:file` for a selected file because plain Mocha also loads the default suite. The script uses the `casai-source` condition and `tsx/esm` loader to run against `src` with the source maps c8 uses for coverage. Mocha strips types. Check `@ts-expect-error` assertions with the relevant compiler profile and run `check` at integration milestones.

The current mock suite covers LLM requests, tools, approvals, history, streaming and errors using SDK mock models and fake provider fetch responses. These contracts do not need a real model. Live tests check actual provider/model behavior. Do not replace them with a generic mock that simply returns each assertion's expected answer; use explicit scripted responses and assert the outgoing requests in mock contract tests.

`test:media:browser` uses Playwright from the Cascada development installation. Use its installed Chromium or set `CASAI_REVIEW_CHROMIUM` to a Chromium executable. It checks prepared PCM, original recorder uploads, the OpenAI multipart serializer and native realtime playback. In the package check, `CASAI_RECORDER_BROWSER` selects the browser for tests against the installed Casai archive. Phase 7 client and 6D composition cases remain planned.

### Writing test fixtures

Provider-backed tests load keys such as `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` from the project-root `.env` via `dotenv/config`. Use the model defaults and spread `...temperatureConfig` from [common.ts](common.ts). For exact-output checks, use a simple marker and a prompt such as “Output exactly MARKER and nothing else.” Avoid numeric decoys close to a familiar number. Use a familiar answer only when the test still requires the cited evidence. For validation failures, use a local Zod refinement when a provider could reject the schema keyword before generation.

In Cascada Script fixtures, use ordinary `var` values and return them directly. Use channels for ordered concurrent collection or streamed text assembly. For a root array data channel, declare `data out`, initialize it with `out = []` before the first `out.push(value)`, and return `out.snapshot()` for the completed array.

## Where the time goes

For a small fix, select the affected cases with `npm run test:file -- <files>` and use `npm run lint:files -- <files>` or the affected compiler profile where applicable. For a browser regression, run the relevant cases together in the browser that exposed it. For example, with the [recorder qualification environment](#browser-recorder-qualification) set for Chrome and FFmpeg, `node --test --test-name-pattern="AAC duration caps|a sole M4A|without a verified frame bound" tests/fixtures/browser-media-contracts.test.mjs` checks accepted copies, rejection before dispatch and WAV fallback in one run.

Batch applicable full browser suites, other engines, clean-package installs, coverage and mutation suites at integration or release. Run one earlier when the change needs that evidence, such as a clean install for a package-export fix. In the handoff, list the pending suite or command and its milestone. Track only suites that cover the change.

`node --import tsx/esm --conditions=casai-source tests/benchmarks/audio/followups.mjs` measures finite scheduling and fresh/reused native worker costs, including the production idle cache; `--pcm-only` omits native measurements. It compares worker-only paths, checks output bytes, and records five alternating trials in `.cache/audio-followups/results.json`. The scheduling control waits for the resample before requesting the result; production shares the same worker cap with bounded resampling jobs and individual worker queues. Native preparation retains one cleaned worker for five idle seconds. See the [measured tradeoffs](../docs/audio-processing-benchmark.md#bounded-finite-scheduling-2026-11-17).

Native release reports are written under `.cache/native-audio-release`. Registry metadata is not platform execution or full license compliance evidence. Run `npm audit signatures` in the project that installed the pinned native dependency and retain the output with the report; the command does not audit linked packages absent from that project's lockfile. See the [platform and distribution status](../docs/phase6-implementation.md#native-release-verification).

`npm run lint` now reuses a successful **whole-check** result only when its content fingerprint is unchanged. It hashes source/tests, emitted declarations, compiler/lint/package settings, generated guide types, matrix/tooling code and installed JavaScript/TypeScript/JSON dependency files. It follows npm links, including Cascada and dependency directories at their real locations. Added/deleted files, changed contents even with preserved timestamps, link targets, relevant environment options and Node versions invalidate the result. Failed checks and arbitrary CLI options are never cached; successful diagnostics are replayed. Inputs are checked again after lint, and a moving target cannot publish a successful cache entry. This differs from [ESLint's ordinary file cache](https://eslint.org/docs/latest/use/command-line-interface#--cache), which does not track imported dependencies.

Use `npm run lint:full` to force a fresh whole-repository lint, including for profiling. The original rules and file targets remain unchanged. `lint:files` also retains every applicable rule and bypasses the whole-check cache. The 64 MiB V8 semi-space setting reduced a representative fresh-process typed-lint probe from 13.6 to 8.8 seconds with byte-identical diagnostics; this is a measured workload, not a guaranteed speedup. It uses a modest amount of additional memory. The native TypeScript compiler already has incremental caches; ESLint still uses the separate TypeScript JavaScript compiler API.

The matrix compiler now stores its native incremental cache in `node_modules/.cache/casai/matrix.tsbuildinfo`, outside the regenerated `.cache/matrix` directory. Every selection is still regenerated, checked and executed as before; TypeScript decides which compiler work can be reused. Guide extraction writes only changed generated contents. `npm run test:checks` maintains cache-invalidation tests, including a real unchanged consumer that acquires a typed-lint error when an imported declaration changes, repeated failures, npm-link changes and preserved timestamps. This check runs in the complete `npm run check` gate.

Use TypeScript 7.0.2 or later for source and emitted consumers and the TS7 language server for editor checks. TypeScript 6 supplies the compiler API for tools such as ESLint. `test:types` uses four main compiler passes.

1. `typecheck:src`: implementation, runtime-test types and compile-only API assertions in one source program (`tsconfig.source.json`). The exact-optional-only fixture belongs to the last pass.
2. `build`: NodeNext compilation and emission of JavaScript and declarations.
3. `typecheck`: runtime-test consumers using emitted public declarations (`tsconfig.consumers.json`). Source files are no longer added as roots. Tests of internal functions still import the internal source they need; they are not excluded or redirected to different implementations.
4. `typecheck:exact`: compile-only consumers of emitted declarations with exact optional properties enabled.

After the build, `component-declarations.cjs` also exports all fourteen inferred component types and annotated function-source wrappers for the specialized families from a physical package consumer, then compiles a second consumer of those emitted declarations under both optional-property modes. The wrapper consumers retain required call inputs and compile under both optional-property modes. This checks usable contracts, portable type names and package exports without another dependency installation.

`npm run test:component-mutations` runs twenty-two focused runtime mutations against the component boundary regression tests. It checks an unchanged control, works in an isolated source copy, and supports a regular-expression argument after `--` to select mutations.

Each no-emit profile uses its own TypeScript incremental cache in `node_modules/.cache/casai`. Source/declaration resolution and optional-property modes must not share a cache file. `typecheck:safety:src` remains an optional focused API check, outside the full gate because its assertions are already in the combined source pass. TypeScript tracks changed inputs and dependencies; caching does not remove assertions or compiler options. Cold checks and broad public-type edits can still be expensive.

The incremental build stores its cache in `dist/.tsbuildinfo`, excluded from the npm package. Deleting `dist` (including `npm run clean`) clears the cache and makes the next build regenerate output. Native incremental builds do not reliably notice individually removed or edited output files: use `npm run build -- --force` to regenerate all output in that case. The source runtime loop needs no build; declaration checks require an up-to-date build, which `test:types` ensures. ESLint cannot reuse the TS7 build's type information and still checks the original source.

Before running an expensive check:

1. Estimate the cost from previous timings, the changed surface and available memory. Start with a focused file or consumer and give exploratory compiler work a short time budget.
2. Run memory-heavy checks sequentially. Schedule type checks, typed lint and editor/mutation matrices around available memory. Leave unrelated browsers and editors running.
3. For a necessary compiler measurement, append `-- --extendedDiagnostics` to the relevant typecheck script. Compare cold and warm runs of the same profile; append `--incremental false` for a cold check. Record wall time separately from compiler check time.
4. Run the full gate once on the settled candidate when warranted. Repeat affected checks after fixes; do not restart every unrelated gate. Poll process completion rather than waiting for log output.

Do not turn off type assertions, lower coverage thresholds or enable dependency-unaware typed-lint caching to obtain a faster green result. If cold compilation remains too costly after memory pressure is relieved, profile the real full consumer program before changing generic types.
