# Test commands and performance

| Command | Purpose | Paid model calls |
| --- | --- | --- |
| `npm test` / `npm run test:local` | Mock-only runtime suite against source | No |
| `npm run test:file -- tests/LLMCalls.unit.test.ts` | One selected file; append `--grep "pattern"` to narrow it | Depends on the selected file |
| `npm run test:watch` | Watch the mock-only suite | No |
| `npm run test:types` | Source, build, consumer declaration emission, emitted-consumer and exact-optional checks | No |
| `npm run test:matrix` | Generate matrix selections; type-check and mock-execute current examples, and check planned examples for syntax and shared sources | No |
| `npm run build` | Incremental package build; reuse unchanged output | No |
| `npm run test:coverage` | Mock-only runtime coverage and thresholds | No |
| `npm run check` | All type profiles, matrix examples, type-aware lint and mock coverage | No |
| `npm run test:live` | Explicit provider-backed integration tests against source | Yes |
| `npm run test:package` | Clean tarball consumer using published dependencies | No |
| `npm run test:package -- --engine C:\Projects\cascada` | Clean consumer using both local package candidates; engine must already be built (a `.tgz` path also works) | No |

`npm test` is the quick runtime loop; it does not check TypeScript assertions. Run the relevant compiler profile for type changes and `check` at integration milestones. `test:live` requires provider credentials in `.env`. The shared mock-only selection lives in `.mocharc.json`, so plain `npx mocha` is also offline by default. Use `test:file` to avoid adding the default suite when selecting one file.

The current mock suite covers LLM requests, tools, approvals, history, streaming and errors using SDK mock models and fake provider fetch responses. These contracts do not need a real model. Live tests check actual provider/model behavior. Do not replace them with a generic mock that simply returns each assertion's expected answer; use explicit scripted responses and assert the outgoing requests in mock contract tests.

The paired package check packs the existing engine build without running its scripts, installs both tarballs outside the workspace, and checks declarations, imports and execution without links. Declaration checks include both optional-property modes and native `ToolSet` annotations. It does not publish or change versions. Passing with a development engine candidate does not establish compatibility with the currently published engine or replace checking the final coordinated release candidates and dependency minimum.

## Where the time goes

The matrix check reads `docs/matrix/matrix.js`, the component renderers and their actual `.cat`/`.cas` sources. Generated files live only in `.cache/matrix`, which is checked to be inside this workspace and cleared before generation. An explicit file list excludes planned APIs from compilation. The check covers option dependencies, every component's `.run()`, inline/loaded resources, tool execution, history/resume, structured output and audio consumption without provider requests. The demo renderer generates only the selected example; exhaustive enumeration belongs to this test command. As the catalog grows, keep focused interaction coverage rather than treating unlimited exhaustive enumeration as a runtime requirement.

The handoff checks also import the private `@casai/matrix` package as a linked dependency, execute all selections from a browser-targeted esbuild bundle, verify selected resource reads and source/Loads transitions, and compile representative real nested exports against the public `.d.ts` contracts. Complete configuration inventories are compared with extracted declarations; displayed native/nested fields must have explanations, and every extracted detail shape must be reachable. Bundling here checks imports and assets without implementing or testing the separate website UI.

The same check verifies the full documentation data in `docs/matrix/reference.js`: the freshly extracted public contract and SDK prose (rather than whole-source-file hashes), registry integrity, property coverage and section references, actual factory previews, source/Loads transitions, invocation-only settings and the distinction between API support and example constraints. It parses the real generated construction to verify `example.configuration` metadata. It checks native prose reuse alongside Casai amendments, checks exact Config alternatives, verifies the declared output fields, compiles a typed documentation consumer and parses catalog/selected exports from `docs:matrix:export` as JSON. Mutation checks reject unknown groups, shapes and unused local properties. Matrix JavaScript/tooling also participates in `npm run lint`. `npm run docs:matrix` refreshes the public-type/native-description inventory and SDK summaries; review that diff and the local adaptations on SDK changes. The separate website consumes this data; no UI is built here. Follow [matrix maintenance](../docs/matrix/MAINTENANCE.md).

Complete Translator examples are explicitly planned. They receive syntax checks and comparison with their executable streaming counterparts, including unchanged setup, invocation and resource files. Their `status`, notice and code comment are asserted. They are excluded from current API compilation/execution, without a fake Translator implementation or declaration; remove that exclusion when the API lands. All current examples still compile and execute with SDK mocks.

`test:types` first extracts all 95 current TypeScript examples directly from README2 into `.cache/readme2`. It also checks all 60 README TypeScript examples: 51 share verbatim source with README2, and nine have their own fixtures. The source and emitted-consumer profiles compile these files, including exact optional properties; examples make no model calls. Every TypeScript fence must have a checking marker, with explicit future-phase skips allowed only in README2 (currently 3). Setup supplies application dependencies and wraps property fragments in concrete components; the example code stays verbatim. Run `node tests/fixtures/readme2-examples.cjs` to refresh them before an individual typecheck.

`test:types` uses four main compiler passes:

1. `typecheck:src`: implementation, runtime-test types and compile-only API assertions in one source program (`tsconfig.source.json`). The exact-optional-only fixture belongs to the last pass.
2. `build`: NodeNext compilation and emission of JavaScript and declarations.
3. `typecheck`: runtime-test consumers using emitted public declarations (`tsconfig.consumers.json`). Source files are no longer added as roots. Tests of internal functions still import the internal source they need; they are not excluded or redirected to different implementations.
4. `typecheck:exact`: compile-only consumers of emitted declarations with exact optional properties enabled.

After the build, `component-declarations.cjs` also exports all fourteen inferred component types from a physical package consumer and compiles a second consumer of those emitted declarations, under both optional-property modes. This checks portable type names and package exports without another dependency installation.

`npm run test:component-mutations` runs twenty-two focused runtime mutations against the component boundary regression tests. It checks an unchanged control, works in an isolated source copy, and supports a regular-expression argument after `--` to select mutations.

Each no-emit profile uses its own TypeScript incremental cache in `node_modules/.cache/casai`. Source/declaration resolution and optional-property modes must not share a cache file. `typecheck:safety:src` remains an optional focused API check, outside the full gate because its assertions are already in the combined source pass. TypeScript tracks changed inputs and dependencies; caching does not remove assertions or compiler options. Cold checks and broad public-type edits can still be expensive.

The incremental build stores its cache in `dist/.tsbuildinfo`, excluded from the npm package. Deleting `dist` (including `npm run clean`) clears the cache and makes the next build regenerate output. Native incremental builds do not reliably notice individually removed or edited output files: use `npm run build -- --force` to regenerate all output in that case. The source runtime loop needs no build; declaration checks require an up-to-date build, which `test:types` ensures. ESLint cannot reuse the TS7 build's type information and still checks the original source.

Before running an expensive check:

1. Inspect previous timing/diagnostic logs, the changed surface and available memory. Start with a focused file or consumer; give exploratory compiler work a short time budget.
2. Run memory-heavy checks sequentially. Avoid overlapping type checks, typed lint and editor/mutation matrices, especially with browsers/editors consuming most RAM.
3. For a necessary compiler measurement, append `-- --extendedDiagnostics` to the relevant typecheck script. Compare cold and warm runs of the same profile; append `--incremental false` for a cold check. Record wall time separately from compiler check time.
4. Run the full gate once on the settled candidate when warranted. Repeat affected checks after fixes; do not restart every unrelated gate. Poll process completion rather than waiting for log output.

Do not turn off type assertions, lower coverage thresholds or enable dependency-unaware typed-lint caching to obtain a faster green result. If cold compilation remains too costly after memory pressure is relieved, profile the real full consumer program before changing generic types. The small type-instantiation budget fixture does not measure full-project cost.

These are bounded source workloads, not runtime call costs or a whole-application timing benchmark. Rebaseline only with an explicit before/after comparison of both import and component costs on the same compiler and workload.
