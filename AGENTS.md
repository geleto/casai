# Agent Notes

## Architectural First Principles

Use these principles when designing, implementing, or reviewing Casai. Derive requirements from the README and specs, but challenge their assumptions when a simpler, more coherent design serves the same purpose.

Before fixing a contract mismatch, first assess whether the contract itself is right. Correct the contract when the existing behavior is simpler and better justified; discuss unresolved design choices with the user.

For implementation reviews, follow [the review process](docs/review-process.md): inventory the whole public surface, trace downstream consumers, compare native behavior, and test interactions and meaningful mutations. Improve the process after each pass and require a subsequent complete pass without important unresolved findings before declaring the review complete.

Do not add defensive complexity for intentionally invalid, malicious, or very unlikely developer code. Handle such cases when the correction is easy and keeps the code simple, or when an end user/model can exploit the boundary. Distinguish developer-supplied configuration from untrusted agent arguments and compare inherited SDK behavior before proposing a workaround.

- **Compose workflows and delegate execution.** Casai should make workflows easier to compose while leaving model execution to the AI SDK and language execution to Cascada. Reuse their contracts rather than maintaining parallel execution machinery. Every additional processing or handling step applied to SDK results needs a concrete purpose; preserve native behavior and avoid redundant work.
- **Inspect native implementations before designing integrations.** Before implementing SDK-facing behavior, inspect the installed `ToolLoopAgent`, SDK `Agent`/tool types, and the core functions they delegate to. Follow approval/history, schema, execution-options, and streaming behavior into the owning modules; read associated tests when available and compare with focused native probes. Reuse native contracts and implement only concrete gaps. Apply this to existing code as it changes, including the [SDK ownership and Phase 2 handoff](docs/plan.md#sdk-ownership-and-phase-2-handoff), rather than reserving it for new factories. Tool-compatible Template/Script components need no fabricated SDK Agent results. See the [native SDK reference](docs/plan.md#native-sdk-reference).
- **Make consistency semantic.** Prefer predictable input, execution, and error rules and reusable machinery. Components need not have identical overloads or result envelopes when their native capabilities differ.
- **Keep shorthand calls primary and usable.** This applies to every callable component in all current and future phases. Inputs accepted by the shorthand caller may remain required at call time. Anything required that it cannot supply must be satisfied by resolved configuration, including inheritance. Reusable `Config` fragments may be incomplete; finished callable components must satisfy those fixed requirements. `.run()` provides named inputs and optional execution overrides on a component whose configuration already meets those fixed requirements. See the [required-configuration rule](docs/plan.md#ordinary-calls-and-required-configuration).
- **Separate configuration from invocation state.** Configuration settings must not be mutated after creation; this is an authoring contract, not a freeze/proxy policy. Components may deliberately mutate authorized state held in context objects or closures, though purity is preferred. Sequence effectful Cascada calls with `!`; hosts coordinate shared state across independent runs. Context snapshots retain their selected top-level bindings, so replacing dependencies/defaults requires a new component or binding for consistent behavior. Isolate each invocation's settings, cancellation, and lifecycle. Result views and adapters must reuse one execution rather than rerunning work.
- **Resolve inputs before schema processing.** Reusable configuration/context may be incomplete, and inputs such as `prompt` may come from the final call. Preserve established merge/override laws and require what remains missing through call types. Separate private configured dependencies from schema-declared application defaults; merge those defaults with direct/model arguments before parsing once. Execute with the parsed application values plus the selected private/trusted bindings. Every schema boundary uses its parsed value, including outputs, stream elements, and custom options. Call/configuration/producer types describe schema input; implementation/consumer types describe output. Preserve precise raw types where original schemas remain available; explicit native SDK tools retain limitations from erased input types, including output-inferred trusted-context settings. Add no machinery to recover that erased information.
- **Keep calls stateless and shared data intact.** Casai's own merging, preparation, and execution must not mutate shared context, nested application data, configuration, or shared schema defaults. Keep execution state invocation-local. Rely on verified native parser copying, not a generic copy planner. Custom validators/refinements/preprocessors/transforms/default/catch factories MUST be pure: leave received/shared data unchanged and perform no external effects; structured transforms return new objects/arrays and copy each nested path they change. Preserve native SDK/Zod parsing behavior, including `.readonly()` freezing borrowed values or shared defaults and the installed Zod 4 behavior on invalid input. These behaviors also occur in native `ToolLoopAgent` and are accepted limitations; add no Casai schema rejection, copying, or freeze-prevention machinery to compensate. Document shared-reference behavior and recommend fresh structured defaults where needed. Cascada's `!` sequences intentional effects on its selected paths, including mutation of authorized application state; it does not synchronize independent runs or make schema callbacks effectful.
- **Represent provenance structurally.** Keep data, executable source, trusted context, and execution controls distinguishable through validation and execution. Do not infer trust from user-controlled markers or intent from ambiguous argument combinations.
- **Promise only what streaming can guarantee.** Promise final application output incrementally only when its finality and stable-prefix semantics are established; keep partial output and execution events explicit. Do not imply whole-result validity before completion. Make consumption, ownership, and cleanup responsibilities explicit.
- **Require abstractions and conveniences to reduce total complexity.** Prefer small, explicit pipelines and successful existing patterns. Question special cases, implicit modes, duplicated paths, and inferred guarantees; evaluate their implementation, typing, testing, and maintenance costs together.

## Merge and Type-Safety Changes

**Closed tool-input decision (2026-10-23):** Casai-created `.asTool` components require explicitly declared top-level public input fields. Reject open-root/catchall tool input contracts; dynamic dictionaries belong inside a declared field such as `attributes` or `payload`. This supersedes earlier open-root Casai tool support, without changing ordinary non-tool components or native third-party tools. Keep one `inputSchema`, configured public defaults, trusted context forwarding and existing private-collision guards. Apply the tool contract consistently through ordinary/named calls on the tool component, SDK binding and injected execution. Do not impose this restriction on `toolContextSchema` or unrelated configuration. Local enforcement is required; provider strictness and JSON metadata alone are insufficient. Reject undeclared raw top-level arguments before application parsing or preprocessing, including for stripping Zod objects and custom SDK/Standard validators. This is independent of provider strict mode. Keep native descriptor executors as parsed-input entry points. See the current decision and implementation status in [the plan](docs/plan.md#remaining-phase-2-decisions).

**Caller-union decision (2026-10-22):** preserve complete checking of union-valued arguments on each component. The user accepts requiring narrowing before calling a union of different components if this simplifies the signatures. Such unions must never weaken required arguments, catchall validation or private-key protection. Preserve contextual callback inference and valid calls after narrowing; this is not a change to merging, runtime validation or configuration inheritance.

**Schema support decision (2026-10-21):** Casai component schemas support Zod 4 Classic/Mini, SDK schemas and Standard Schema. Reject Zod 3 in directly supplied input, output, tool-context and stream-element schemas, in types and at runtime. Do not restore legacy discovery code. Native third-party tools and SDK output specifications retain native SDK support; do not inspect their internal schemas. This supersedes older Zod 3 acceptance examples in historical proofs.

**Security revision (2026-10-19):** model-controlled arguments must not replace private execution data. This supersedes older permission for open-schema private overrides. Keep one application inputSchema and preserve trusted dependency forwarding through configuration/tool context. The [private-boundary investigation](docs/phase2-private-boundary-review.md) demonstrates protection of identifiable private names and schema-backed ordinary forwarding; type-only/undeclared absent names are an accepted authoring limitation. The [decision record](docs/plan.md#remaining-phase-2-decisions) retains the explicit-public-declaration direction: no-schema configured fields have no public declaration, while unrelated extras remain allowed on ordinary non-tool components. Registered-tool-name protection is confirmed; executable fallback names reject retained undeclared caller collisions, preserving configured/trusted and explicitly public shadowing. The override/strictness discussion is resolved: add no blanket private-protection bypass; schema openness controls unrelated extras on ordinary non-tool components. Current-source security corrections belong to Phase 2; no separate maintenance delivery question remains. The [combined runtime/callable proof](docs/phase2-composed-api-proof.md) now establishes bounded feasibility for the shared Function slice, including no-schema and registry cases. Final factory/consumer integration is still required; do not claim the production API is proven or Phase 2 is complete. Bare tools accept private-only native context; incoming public defaults require explicit binding. Use the newer chain-resolution runtime, with no legacy-runtime patches. Its compiler/renderer handoff is an acceptance dependency, not completed by kernel tests, and read-only references do not resolve argument provenance. Do not add a second input schema, global identity freeze, or model-origin tracking.

The [hybrid evaluation](docs/phase2-private-boundary-review.md#hybrid-evaluation-closed-input-plus-protected-open-input) extends the isolated proof to supported declared optional context names and protected ordinary-child forwarding. The user accepted protection of actual private runtime properties, including own `undefined`, plus supported declared private names. Actual private properties require no context schema; an absent name present only in a type or author intent is an authoring limitation, not an unidentifiable existing binding. Do not use arbitrary public extras as trusted identity. Context output declarations differ from raw input metadata; do not substitute one for the other or discard known bindings when complete output discovery is unavailable. This limitation does not require globally closed inputs, private namespaces, or opaque-schema rejection. Provider strictness and metadata-only `additionalProperties: false` do not establish local validation. The [verified strict defaults and scope](docs/phase2-private-boundary-review.md#provider-strict-mode-defaults-and-scope) distinguish provider generation from runtime protection; do not claim strict mode is globally enabled or the entire issue exists only when it is off. Keep final factory typing, UI/renderer integration, and the chosen newer runtime handoff as explicit acceptance gates.

The user confirmed closed-shape caller typing: reject undeclared fields for both strict and stripping closed shapes; retain native extra-field types for open/catchall schemas on ordinary components and native SDK tools. Casai tool admission follows the closed-root decision above. Zod 4 does not expose a type distinction between strict and stripping objects. Runtime application validation follows the schema, subject to the security boundary above. Check effective closed union branches after the established shallow merge; changing a discriminator does not remove old configured fields. The [public API/type proof](docs/phase2-public-api-proof.md) demonstrates the bounded admission and binding design, source/emitted declarations, callback completion, and both optional-property modes. Reuse its checks during production integration; it does not implement Phase 2.

The earlier Phase 2 proofs close their bounded feasibility gate, but do not establish the later private-data security requirement. Their established results include schema admission, usable call signatures, and the external `bindToolContext` contract under the earlier policy. The [combined proof](docs/phase2-composed-api-proof.md) now composes those guards in one implemented candidate, with no-schema configured-name and registered-tool-name protection, raw/default-aware helpers, optional shadow types, named diagnostics and a measured representative type-cost budget. Reuse its runtime/source/declaration/editor/mutation checks during the Function slice; compose final inherited implementation/schema compatibility and measure production-wide cost at integration. Production integration must still meet the [schema capability and public signature gate](docs/plan.md#schema-capability-and-public-signature-gate) acceptance criteria, including root unions/composition with unrelated private configuration, diagnostics that name rejected keys, and a type-check cost budget. Keep runtime and type cases paired; do not silently weaken configured-default or union/optional guarantees to make either side pass.

Preserve established merging and type-safety behavior. Proceed without confirmation when a decision is straightforward and clearly improves validation. Discuss non-obvious changes to merging, validation order, or accepted types, and obtain confirmation when there are meaningful behavior or inference tradeoffs; explain the concrete consequences. The [confirmed decisions](docs/plan.md#confirmed-schema-and-context-decisions) authorize merge-first parsing on direct and tool paths, schema-controlled application input followed by ordinary context merging on every entry path, parsed values at every schema boundary, and removal of the generic copy planner. Phase 2 specifies the SDK tool wrapper/projection needed to honor configured declared defaults without publishing private data. These are targets, not claims about current factories, and do not authorize unrelated merge/inference changes. Named schema declarations select configured public defaults; other configured/trusted values must not be copied into the SDK argument validator. The selected metadata follow-up advertises only supported JSON-valued public defaults whose effective source is configuration, never private or incoming bound-context values; preserve the plan's annotation-only limits and original schema identity. The input schema controls application parsing, but its acceptance cannot authorize a model to replace a private dependency. Preserve configured public defaults and parsed values while resolving the security boundary before integration. An open schema neither publishes all configuration nor permits private replacement. A child's input schema does not limit unrelated inherited configuration; do not require a general config schema.

Casai must not trial-parse incomplete fragments or run callbacks to discover schema ownership/defaults or whether a schema accepts missing input. Enforce schema-dependent configuration requirements through factory types; runtime schemas validate effective invocation values. Optional Casai `.asTool` configuration uses only `toolContextSchema`. Forbid top-level `contextSchema` in all Casai configuration and reusable fragments, including inherited configuration: reject it in types and with runtime `ConfigError` directing authors to `toolContextSchema`, even when explicitly `undefined` or both names are present. Scope this check to Casai configuration, not native tools inside `tools`, SDK-facing descriptor properties, or application data inside `context`; inheritance reads the parent component's `.config`. Add no alias or recursive key ban. The returned tool-compatible component maps it to native descriptor `contextSchema`, preserving schema identity. This is an SDK Tool compatibility property; the SDK Agent interface has no such member, and ordinary components need none. It validates incoming `options.context` only; ordinary calls neither extract configured trusted fields nor parse `config.context` through it. Final callable types must still satisfy implementation dependencies on the ordinary path. Registry calls preserve the native `toolsContext` entry, including `undefined`; do not normalize it to `{}`, substitute configured dependencies, or trial-parse alternatives. All components with registered tools support the owner's `toolsContext` map. Tool-context validation needs no JSON metadata conversion. The confirmed source priority is arguments over tool context over `config.context`; do not let configured defaults acquire caller priority merely by inserting them into parsed arguments. The [isolated SDK proof](docs/phase2-input-adapter-proof.md) demonstrates that the fixed standalone descriptor cannot preserve this overlap priority and fully resolved parsed SDK input together. The user selected per-run binding for exploration and confirmed immutable context for the whole binding lifetime. The extended prototype demonstrates that boundary: create a new descriptor/context pair per binding, never mutate the component, and keep all bound context fixed across steps. New independent invocations may bind different inputs. Direct SDK consumers supplying public defaults through context need explicit binding; private-only context can use the bare descriptor; Casai owners bind internally. Production implementation is not part of this proof. Do not treat this as a merge-order-only implementation fix. Configured public values satisfying required input fields is confirmed, including inheritance. Both shorthand and `.run()` validate caller types against schema input, allow omission of schema fields guaranteed by resolved configuration, and ignore unrelated configured properties when deriving public arguments. Keep the original complete-input schema required; do not substitute caller-only validation. Do not implement the conflicting wrapper as settled behavior.

Configured public-default selection is retained. The [default-resolution proof](docs/phase2-default-resolution-proof.md) recommends selecting all declared fields, including optional/defaulted ones, before one complete parse. Use bounded public Zod declaration access, otherwise SDK/Standard input metadata; opaque schemas needing partitioning must supply explicit metadata. The selected bounded union extension reads one level of declared object-branch names for partitioning, without branch selection or model-schema rewriting. Source-free local validation must not require declaration discovery. Union tools with public defaults remain outside the supported projection. The combined proof supplies paired runtime/callable cases for direct one-level unions and private-only union tools; keep broader composition and full projection outside that evidence. Promised metadata resolves before execution without asynchronous factories. Declaration discovery selects defaults for ordinary components; for Casai tools it also supplies the pre-parse top-level allowlist. Do not impose JSON-only restrictions on JavaScript/Cascada input or treat successful parsing as proof of metadata support. Follow the [preparation contract](docs/plan.md#context-sources-and-preparation), including its immutable binding pipeline and bounded declaration capability, not a parallel Zod interpreter. Partitioned root preprocessors consume application values under declared input names; use a declared raw object schema followed by a transform for renaming. Engines and prompt renderers must not restore raw application defaults removed by a transform. Where tool projection removes a root required entry, reject schema references at schema-valued positions rather than resolving or rewriting them; literal `$ref` keys in data do not count. Unchanged native schemas retain native support. Native SDK/Zod JSON Schema conversion may evaluate pure default factories; preserve that behavior without promising exactly-once callback execution or caching metadata-time defaults into invocation context. Binding may lazily parse captured tool context once to select public defaults and retain fixed binding-local preparation facts. Do not cache a mutable current context on the component or original schema. No redundant Casai application parse does not mean exactly-once native context validation: SDK input hooks, approval, and execution may independently parse trusted context. Preserve those native SDK boundaries rather than caching or suppressing their parsing. The selected injected-call follow-up reuses a Casai binding's already-parsed fixed context; plain native tools without that binding keep per-call context validation. Default-factory objects can therefore be shared across injected calls within one binding under the purity contract. SDK history/approval revalidation is a separate boundary from fresh tool argument parsing. Where public defaults participate in validation, keep them stable across approval continuation; changing revalidated input can prevent execution through a native SDK tool error. Keep transformed public tool arguments distinct from private execution context, and compare multi-turn UI behavior with the native SDK. The documented native SDK limitation for transformed arguments in UI history is accepted; add no Casai workaround or completion gate for it.

The [confirmed delivery typing](docs/plan.md#final-application-output) authorizes a union of possible streaming `value` delivery types when an explicit SDK output type does not distinguish its kind. Preserve precise known/default kinds, inferred completed/element types, and the planned runtime delivery. Add no output wrapper, kind selector, or schema rewrite to recover erased type information. This includes object, array, and custom outputs whose `name` is only typed as `string`; distribute over output unions and do not infer the kind from a native element stream. Native SDK result-property types remain unchanged.

Preserve the [native continuation-setup limitation](docs/plan.md#output-availability-and-failures): the SDK can report a later preparation/provider-call error while resolving earlier completed steps. Casai follows the SDK-reported final step; add no separate failure tracker to compensate. Keep retry error attribution scoped to the model attempt and characterize native exceptions when upgrading the SDK. Preserve the documented native generation cancellation-during-tool limitation too; do not add an abort listener to reinterpret a normally returned SDK result. Native stream completion promises own abort/timeout/thrown-stream errors, with one completion-error check using native overall and final-step finish reasons; SDK stream transforms can change these independently. SDK stream transforms feed both final output and stream views and do not alone require buffering. Keep approval-ID denial handling: streaming provider denials can lack synthetic tool results.

Phase 2 replaces both automatic `_toolCallOptions` injection and the earlier callback-only options parameter with reserved `context._toolOptions` for every component body and `.withFunction` preparer. Derive the shared public `ComponentExecutionOptions` from a type-only import of SDK `ToolExecutionOptions<unknown>`, omitting `context` because its parsed fields are already flat and making only `toolCallId`/`messages` optional for ordinary invocations. Infer this type for Function and preparation callbacks; preserve other native options/types, including optional sandbox support. Native SDK descriptor executors retain full `ToolExecutionOptions<CONTEXT>`. Ordinary calls expose `{}` or their explicit `abortSignal`, with no fabricated tool metadata. Inject actual metadata after application parsing/merging; input/configuration cannot spoof it or authorize skipping validation, and real metadata must not enter SDK public argument records. Native SDK tools/descriptors retain `execute(input, options)`. Injected wrappers normalize Cascada keyword arguments before schema validation and reuse the same bound descriptor and matching captured raw context as SDK calls. Phase 2 applies shared correctness fixes to retiring Text/Object factories without adding their new LLM public APIs. Phase 3 establishes LLMAgent rendered calls as `(context, messageHistory?)` or `(source, context, messageHistory?)`, including function preparers, rejects old unmarked history-before-context orders, and implements its full preparer tool registry. Preserve existing factory call forms until replacement; do not add preparation registries/types to Object factories. See the [Phase 2 scope](docs/plan.md#phase-2-existing-component-foundations).

Result history assembles native `responseMessages` when available and preserves their rejection; do not gate history on execution success or `value` eligibility. Treat every literal/prepared prompt string, including empty text, as a user message regardless of history. TextGenerator tools return parsed final `value` and infer its type from the merged output setting. Fresh result getters reuse one execution and parse; custom parsed iterables retain their own consumption/cleanup rules without a Casai replay layer. Phase 2 also supplies explicit `toReadableStream` conversion and re-exports Cascada's `makeSharedIterable`; sharing is opt-in, with native retention/disposal semantics and no automatic replay. Custom `Output.name` selects delivery, so `array` requires an iterable parsed value.

## Cancellation Scope

Cancellation signals belong to invocations: reject `abortSignal` in reusable configuration, including inherited configuration, and retain it on LLM `.run()`. Phase 1 LLM tool adapters forward the SDK tool-call signal through `.run()`. Phase 2 keeps that explicit forwarding through the shared internal prepared-execution path, avoiding another raw-input parse; this boundary needs no async call context. Phase 2 extends explicit cooperative forwarding to coded-component `.run()` and injected registered tools, capturing signals in invocation-local wrappers without interrupting rendering or automatically reaching arbitrary context functions/components. Keep this to argument forwarding and immediate checks: add no Casai controllers, abort listeners, signal merging, timers, races, or call tracking. Discuss and defer any path needing such machinery to the appropriate later phase. Until [Phase 7](docs/plan.md#phase-7-async-call-context-and-deadlines), preserve native SDK per-call `abortSignal` and `timeout` settings unchanged, await preparation normally, and check an explicit caller signal before SDK dispatch. Shared deadlines require Cascada async call context, developed with telemetry, not native engine abort. Propagate an absolute end time and call ancestry implicitly; each child takes the earlier of its parent end time and its own timeout from entry. Create signals only at boundaries that need them; do not restore a generic signal-dependent `createInvocation` scope or a parallel call tracker. Once that context exists, timeout races for Function/Script/Template are acceptable before native abort, with continuing work retaining its expired context so nested calls cannot escape the deadline. A race rejects the wait; it does not stop arbitrary JavaScript or unsupported engine work. Keep this handling minimal in each invocation and preserve native SDK limitations. See [the deadline contract](docs/abort.md).

## Tests

Do not run the whole suite by default. LLM-backed tests cost time and money.

Run one file with:

```bash
npm run test:file -- tests/Script.test.ts
```

`npm run test:file` uses the `casai-source` export condition and runs tests against `src`. Its `tsx/esm` loader keeps execution and c8 source maps consistent; mixing CommonJS and ESM transforms produces misleading coverage.

Mocha strips types, so the `@ts-expect-error` type tests are checked only by the compiler, in `test:types`.

- `npm test` and `npm run test:local` run the mock-only runtime suite, without compilation or paid calls. Add new mock-only files to `.mocharc.json`, the shared selection for these commands and plain Mocha. `npm run test:watch` watches that same suite.
- `npm run test:live` explicitly opts into the provider-backed files and may make paid calls. Those files mix provider checks with local assertions; move new local-contract coverage to mock-only files instead of requiring a provider. Use scripted SDK mocks (or fake provider fetch responses) for request, tool, stream and error contracts; reserve live tests for actual provider behavior.
- `npm run test:coverage` runs that mock suite with c8 and writes source-mapped text, JSON, and HTML reports to `coverage/`. It checks runtime-source coverage and the shared augmentation core separately; declaration-only types use `test:types`.
- TypeScript 7.0.2 is the minimum supported compiler. `npm run test:types` checks source consumers with TS7, builds, then checks `dist` consumers and both optional-property modes. Editor checks use the TS7 language server. Keep TS6 only as a development dependency for tools such as ESLint that require its JavaScript compiler API; it is not a compatibility target.
- `npm run check` runs `test:types`, `lint` and `test:coverage`: everything that needs no paid LLM calls.

Budget checks before starting them. Use focused runtime/type/lint checks while iterating and the complete gate at integration milestones; do not repeat editor and mutation matrices after unrelated edits. `test:types` combines source and API assertions, builds, checks runtime-test consumers, then exact-optional API consumers: four passes. No-emit profiles have distinct incremental caches under `node_modules/.cache/casai`; the optional `typecheck:safety:src` is for focused work and is not duplicated in the full gate. The build cache lives in `dist/.tsbuildinfo`, so deleting `dist` also clears it. Use `npm run build -- --force` if individual generated files were removed or edited. For a cold comparison, append `-- --incremental false` to a typecheck script. Keep all compiler options, lint rules and source/declaration coverage intact. See [test commands and performance](tests/README.md).

Run compiler-heavy checks sequentially, inspect available memory before starting, and use a time budget for exploratory profiling. Capture wall time and compiler diagnostics rather than treating quiet output as a hang. Poll the command's completion status, not only its log. Do not start the full gate just to estimate its duration, or kill unrelated browser/editor processes to make room. Type-aware ESLint uses TS6 and can be memory-heavy; do not enable its per-file cache without accounting for changes to imported types.

Add `-- --grep "pattern"` after the filename for a single test or group.

`.mocharc.json` lists the mock-only suite, so plain `npx mocha tests/File.test.ts` adds that file to the default suite and is not a true single-file run. Use `test:file` for a selected file.

Configured application values and schema defaults can satisfy requirements on direct and SDK-tool paths, including empty arguments. Parse final merged application input once, keep private/trusted bindings separate, and use returned values everywhere. Test raw/parsed types, missing fields after configuration, public overrides and private collision/forwarding cases on every path, open/stripping/strict inputs, and unrelated inherited bindings, advertised SDK requirements, and absence of private sentinels from history/UI/next requests. Verify Zod 4 Classic/Mini ordinary copying with frozen and unfrozen fixtures. Characterize shared nested defaults, fresh/shared default/catch factories, `.readonly()` wrapper ordering, and freezing on invalid input against native SDK behavior; do not turn inherited behavior into a Casai rejection or copying requirement. Recheck version-specific probes on dependency upgrades. Native output/stream and custom options also use parsed values, lazily for stream elements. The production factories now use `src/execution.ts` and `src/schema.ts`; the [implementation ledger](docs/phase2-review.md#production-integration-2026-10-20) distinguishes their verification from the outstanding newer-runtime handoff and release gates.

## Current Script Notes

Prefer direct script return values. Use `data` or `text` channels only when the test needs ordered concurrent collection or streamed text assembly.

Prefer regular `var` values whenever they are sufficient; do not introduce channels for ordinary structured data.

For root array data channels, initialize before pushing:

```cascada
data out
out = []
out.push(value)
return out.snapshot()
```

## Provider Quirks

Use `...temperatureConfig` from `tests/common.ts` in LLM test configs; do not pass `temperature` directly.

For exact-output tests on small models, use simple marker strings unless punctuation is the behavior being tested.

Avoid near-famous numeric decoys, Use famous numbers in exact known answers for cited output, but not when this allows guessing a test-derived answer.

Anthropic may reject some JSON-schema keywords before generation. For validation-failure tests, prefer local Zod validation such as `.refine(...)` instead of provider-level numeric bounds.

Exact-output LLM assertions need strict prompts such as `Output exactly ... and nothing else`.

## API Imports

With current ESM packages, type-only exports must use `import type`, for example `ToolExecutionOptions`, `ModelMessage`, `StreamTextResult`, `LoaderInterface`, and `ILoaderAny`.
